# Stage 7 — подготовка nonce-кандидата и SHA-256 midstate

**Модульные исходники и библиотеки. Это не готовый cgminer и не прошивка.**
Физический ASIC, пул и сервер не использовались и не изменялись.

Продолжение архива Stage 6 с SHA-256
`853a60107f192fbb148b998fd250630e12a271edc4abf575bd0eb626f0637ead`.
Оригинальный `reference/cgminer.vendor.elf` сохранён без изменения, 6 228 004 байта:
`b2663b3aa753cc14ae9d3b11a14d3d93c74b605a3e433b02101c3c17c69d95e9`.

## 1. Следующий участок после приёма кадра

В `src/backend/work-gen/work-gen.c` перенесён исследованный путь
`0xc4480–0xc46fc` (последняя граница не выполняется):

```text
nonce-кадр, уже выделенный Stage 6
    ↓
5-битный слот задания, 0–31
    ↓
предоставленная вызывающим кодом согласованная копия записи задания
    ↓
преобразование битов версии и извлечение nonce
    ↓
chip/core attribution через явные обработчики
    ↓
сборка 64-байтного блока и одно сжатие SHA-256
    ↓
68 явно заполненных байт кандидата
```

Это **подготовка кандидата**, а не проверка его хеша относительно target,
не поиск полного задания у пула, не проверка его актуальности и не accepted share.
Запись в оригинальную очередь и её потребитель ещё не восстановлены.

### Таблица заданий

В исследуемом ELF адрес записи: `0x653460 + slot * 168`.
Присутствующая рядом исходная запись таблицы копирует 168 байт и оборачивает индекс
после 31. Это проверенная геометрия таблицы, не восстановленный менеджер заданий.

Новый API принимает согласованный неизменяемый 168-байтный снимок. Указатели из
снимка не разыменовываются. Слот может переиспользоваться: сам индекс **не доказывает
свежесть задания**, и API не приписывает ему выдуманный номер поколения.

### Биты версии

Для формата `variant == 2` используются два байта payload[6..7] в big-endian.
Для двух прежних форматов оригинальный код подставляет `0xffff`, **не ноль**.
Перестановка в C сохраняется буквально:

```c
(v >> 11) | ((v & 7u) << 21) | ((v & 0x7f8u) << 5)
```

Результат объединяется OR с исходным словом записи задания. Это не объявляется
полной реализацией pool version-rolling или согласованием его маски.
Все 65 536 значений двухбайтного поля сравнены с исходными ARM-инструкциями.

### Заполняемые поля кандидата

В новом компактном типе находятся chain_id, chip_id, core_id, сырое слово записи
по +0xa4, индекс слота, слово версии, сырые слова по +0x70/+0x74, nonce и восемь
32-битных слов midstate. Неподтверждённым полям не присваивались предположительные
названия вроде времени, сложности или указателя.

Вариант 1 извлекает nonce со смещением одного байта, остальные — с нулевого;
четырёхбайтное значение читается как big-endian. Chip/core-обработчики вызываются
по одному разу, в этом порядке. Их значения сохраняются без выдуманной проверки
физических диапазонов или полноценного восстановления общего диспетчера.

## 2. Важное различие: 68 заполненных байт против очереди 72 байта

Исследованный producer пишет **68 байт**, однако оригинальная инициализация
по `0xfa5c4` задаёт **72 байта на элемент** очереди, ёмкость 4096 элементов.
Последние четыре байта этот участок не записывает. В 864 тестах они заранее
заполнялись маркером `a1b2c3d4` и проверялись на неизменность.

Назначение этих четырёх байт не установлено. Padding — лишь гипотеза.
Поэтому `vn135_nonce_candidate` **не совместим побайтно с полным исходным ABI
очереди**. Его нельзя передавать вместо 72-байтного элемента в оригинальный
потребитель. В заголовке явно раздельные константы 68 и 72; нет чтения лишних
четырёх байт, фиктивного поля с придуманным смыслом или неявной вставки в очередь.

## 3. SHA-256: настоящее вычисление, не заглушка

Новый `reconstruction/support/sha256_midstate.c` содержит переносимую процедуру
сжатия одного 64-байтного блока и получение midstate от стандартного начального
состояния. Имена этого support-файла/API новые: исходное имя файла SHA-библиотеки
производителя здесь не объявляется восстановленным.

Midstate — состояние после одного блока, **не полный SHA256d-хеш nonce-кандидата**.
В новом API нет потокового финализатора или автоматического padding. Стандартное
дополнение добавляет только независимый тест для сравнения с Python `hashlib`.
Не подменяется публичный upstream `sha2.c` и не создаётся конкурирующий main.

При сравнении кандидатов реально выполняются оригинальные процедуры
`0x109120` (init), `0x109170` (update) и `0x108b7c` (compression). Их результат
**не подставляется тестовой константой**. Отдельно исходный финализатор
`0x10939c` используется в 20 проверках полного SHA-256 от 64-байтных сообщений
против `hashlib`; это тестовая процедура, не обещание восстановления всего API.

Сборка блока подтверждена побайтно. Интерпретация всех исходных полей как полного
80-байтного заголовка Bitcoin ещё не доказана и в интерфейс не зашита.

## 4. Отдельный helper определения core

В `libbitmain/src/chip/chip1398.c` добавлено битовое преобразование из `0xed974`:

- числовой model ID `0x1398`: `nonce >> 24`;
- `0x1397`: `((nonce >> 21) & 0x3fe) | (nonce >> 31)`;
- остальные значения: `0`.

Числовой model ID здесь не смешивается с селекторами платы/чипа 0–7. Общая
маршрутизация chip/core в producer остаётся внешними callbacks.
**Это не подтверждает привязку T21 к chip1398 и не подтверждает валидность nonce.**

## 5. Новый адаптер — отдельно от исходного кода

`reconstruction/support/work_nonce_pipeline.c` соединяет Stage 6 RX с новым
обработчиком. Проверяет согласованность формата, nonce-флаг и индекс слота;
вызывает reader снимка ровно один раз. Без записи возвращает `NO_JOB`, при ошибке
reader — `LOOKUP_FAILED`. В этих случаях выход не изменяется, chip/core callbacks
не запускаются. Неверные аргументы/форматы отклоняются до внешних вызовов.

Нет аллокаций, скрытых повторов, потоков, аппаратных записей, обращения к пулу
или подстановки задания из другого слота. Согласованность снимка и управление
жизненным циклом задания являются обязанностью вызывающего кода.

| Новый набор | Успешных случаев |
|---|---:|
| Кандидат: 68 байт, блок 64 байта, порядок вызовов, неизменный хвост очереди | 864 |
| Биты версии variant 2: все uint16 | 65 536 |
| Биты версии двух прежних форматов | 266 |
| SHA midstate от стандартного IV | 132 |
| SHA compression от произвольного состояния | 132 |
| Оригинальный полный SHA-256 и hashlib на 64-байтном сообщении | 20 |
| Helper core по исходному ARM | 1 305 |
| **Новые сравнения с оригинальными инструкциями** | **68 255** |

| **Совокупный набор сравнительных случаев** | **96 439** |

Большое число обусловлено **65 536 входами одного небольшого преобразования**,
а не восстановлением десятков тысяч новых функций. Остальные новые сравнения
с оригиналом — 2 719 случаев. Повтор всего нового набора на Clang также прошёл;
он не прибавляется к количеству уникальных тестовых входов.

Отдельные проверки, не включённые в указанную сумму:

- 104 сообщения с корректным padding, новый SHA-helper против `hashlib`;
- 3 536 синтетических тестов добавленных UXTH/SMLABB в локальном интерпретаторе;
- 176 нативных потоковых прогонов RX → snapshot reader → candidate с фрагментацией
  от 1 до 11 байт, плюс проверки отказов и известных SHA-векторов;
- GCC/Clang C-тесты и ASan/UBSan с проверкой утечек нового нативного набора;
- повтор прежних Linux PTY/UART/RX тестов; новых испытаний физического UART нет.

### Границы эталонного сравнения

Используется локальный ограниченный A32-интерпретатор, не независимо
сертифицированный эмулятор. Добавлены UXTH и SMLABB, проверена в том числе
накопительная семантика Q для переполнения; неподдерживаемые инструкции
останавливают тест. Это не исполнение полного бинарника как Linux-процесса.

В candidate-тестах внедрены chip/core attribution и memcpy; SHA оригинальный.
В тесте core внедрён getter числовой модели. В отдельной SHA-финализации
внедрён memset. Запись задания, очередь/потоки, гонки, смена поколений, реальные
UART/хешплаты/PSU не эмулируются. Равенство на этих входах не доказывает все
ветви прошивки, аппаратную безопасность или принятые пулом шары.

## 7. Сборка, структура и воспроизведение

```sh
make -f Makefile.recovery clean
make -f Makefile.recovery all test arm evidence-check sanitize
make -f Makefile.recovery stage7-clang
make -f Makefile.recovery linux-pty sanitize-linux-pty
make -f Makefile.recovery linux-pty-rx sanitize-linux-pty-rx
python3 tests/test_assembler.py
python3 tools/update_overlay_inventory.py --check
```

Тесты нового этапа отдельно: `make -f Makefile.recovery stage7`.
Групповая проверка чистого архива: `tools/verify_stage7.py`, группы
`build core cache uart rx nonce clang-nonce sanitizers evidence full-runtime-blocked`.
Логи передаются параметром `--logs` в каталог **вне дерева исходников**.

Сохраняется 46 наблюдаемых исходных путей, 6 частично восстановленных файлов,
40 невосстановленных исключены из сборки. Компилируется 10 C-единиц:
6 на наблюдаемых путях плюс 4 явно новых support/adapter-файла.
Это не процент готовности. Монолитных файлов и функций-заглушек с фиктивным
успехом не добавлено.

Выход: host `.a`/`.so` для проверок, ARMv7-A/A32 hard-float freestanding `.a`
без Linux sysroot. **Не исполняемый cgminer.** Механизм наложения на выбранный
public cgminer сохранён; полное дерево upstream по-прежнему не включено, совместная
сборка полного cgminer на данном этапе не выполнялась. Сетевой доступ для этой
работы не требуется, новый поиск/скачивание upstream на этом этапе не заявляется.

Карты исходных байтов/адресов: `evidence/stage7/recovery-manifest.json`.
Четыре листинга помечены context-only (стек/таблица/очередь), не считаются
восстановленными реализациями. Проверка связей: `tools/check_stage7_evidence.py`.
Протоколы: `evidence/validation/stage7/`. Патч:
`evidence/stage7/review/stage6-to-stage7-source.patch`.

Остались CRC ответов, полный SHA256d/target-контроль nonce, lifecycle заданий,
потребитель очереди, T21 model dispatch/запуск цепей, PSU/датчики/защиты,
регистрация драйвера cgminer и автотюн. Ничего не установлено на ASIC.
**Не заменять штатный `/usr/bin/cgminer` этими библиотеками.**
