# L-15: границы групп BM1368 и UART relay, регистр 0x2c

Ниже сохранено описание пакета от 2026-10-02. Актуальная база и границы новых
испытаний указаны в разделе «Интеграция после PR114 (2026-10-03)».

Статус: проверенный на host кандидат. Не полноценная прошивка и не готовый
драйвер T21. База work/reconstruction: 01299b84255542c16ee6d3f0c65a3e33e7aa876a,
дерево 69b65cf5413866bd1971e0d1b01412cf443c8f92. Никакой код L-14 или R13–R17
не импортирован; это независимое продолжение после опубликованного L-13.

## Реальный новый код

`vn135_bm1368_set_uart_relay_135` восстанавливает метод оригинального cgminer
по адресу e4690. Он один раз вызывает уже существующий writer: unicast,
регистр 0x2c, значение `3 | (setting << 16)` с 32-битной арифметикой.
Любой ненулевой результат writer даёт диагностическое сообщение и -1.
Индексы цепи и чипа для диагностики читаются ПОСЛЕ writer и увеличиваются
на единицу по модулю 2^32. Индекс чипа берётся из cache_index, не wire_address.
Оригинальная строка: `chain#%d chip#%d - failed to config UART relay`, line 721.
Отправка уже могла состояться, когда кэш вернул ошибку: транзакционного отката нет.

`vn135_bm1368_configure_group_boundaries_135` восстанавливает обычный граф
вызовов b5568. Прямой вызов этого участка виден в координаторе по адресу 56844.
Кандидат обходит границы групп, формирует отдельные временные описатели первого
и последнего чипа и передаёт их выбранному методу. Сохраняются порядок чтения
флагов, захваченные owner/board, перечитывание изменяемых полей после callback,
один setting на два вызова внутри прохода и немедленный выход -1 при ошибке.

Нулевой шаг не исправляется выдуманным значением: оригинал способен зациклиться.
Контракт требует завершающуюся последовательность состояний/результатов. В тесте
нулевой шаг проверен четырьмя повторами с явной ошибкой четвёртого callback, а не
зависанием. Полные 32-битные значения, signed-порог count<10, бит знака после
вычитания и переполнение адресной арифметики сохранены без signed overflow в C.

## Граница доказательств

Оригинальный ELF SHA256:
`b2663b3aa753cc14ae9d3b11a14d3d93c74b605a3e433b02101c3c17c69d95e9`.
Прочитан как данные, не запущен. Свидетельство содержит 15 диапазонов / 1387 байт,
39 фиксированных слов инструкций, семь прямых переходов, четыре строки и 22
контрольные суммы исходных файлов. Python-проверка работает и с `-O`.

Семантическое сопоставление исходного графа и C — ручной статический разбор,
не автоматическое доказательство эквивалентности и не независимый внешний review.
Opaque parity ветки исключены только в области обычной корректной памяти: у
`x*(x-1)` младший бит всегда нулевой. Faults, нарушения ABI, гонки и неподходящие
указатели не моделируются. Предполагается нормальная однократная инициализация
строк; для общих driver/source/function используется уже зафиксированное L-13
свидетельство, для новой строки сохранён отдельный XOR-инициализатор e5a6c.

e4690 относится к исходному chip/chip1368.c; новый файл chip1368-group-boundary.c
является явным integration split, а не якобы восстановленным названием файла.
Для b5568 исходное имя файла не установлено. C-структуры — типизированные host
представления, не оригинальная ABI-разметка. Конструктор BM1368 хранит e4690 как
числовую идентичность в слоте b0; существующий owner+1c0 вызывается косвенно.
Тест явно связывает callback с восстановленным методом, НЕ выдавая эту привязку
за восстановленный runtime-инсталлятор таблицы методов.

## Проверки, выполненные для этого кандидата

GCC 14.2 и Clang 17: каждый обычный прогон — 66 517 сценариев / 1 131 053 проверки;
каждый обнаруживает 21 отдельно скомпилированный семантический дефект через
ожидаемое assertion и exit 1. Crash, timeout и ошибка компиляции не считаются
обнаружением. Большая часть сценариев — полный перебор 65 536 значений поля,
а не столько различных аппаратных режимов.

Те же 66 517 сценариев прошли GCC и Clang с ASan/UBSan. Все семь непосредственно
собираемых единиц трансляции инструментированы. Leak detection отключён: проверки
отсутствия утечек не заявляются. TSan, ARM-сборка, полный native runtime и ASIC
не проверены. Команда завершает путь записывающим fixture: никаких UART/pool I/O.

Полная композиция вызывает НАСТОЯЩИЕ новые caller и bridge, существующие writer,
encoder/CRC и реальный reg_cache. Проверены четыре последовательные команды,
ошибка отправки обоих знаков в каждой позиции и ошибка реального кэша после
второй записанной отправки. Остальные сценарии проверяют мутации состояния,
нулевой шаг, границы целых чисел и точные диагностические аргументы.

Неизменённые регрессии: register-write/frequency — 2360 сценариев / 64853 проверки;
control bounds — 6455 проверок / 1088 reset cases; L-13 address-команды — 315
сценариев / 4318 проверок (GCC обычный, Clang ASan/UBSan). Эти числа не суммируются
в процент готовности прошивки. Полные журналы входят в пакет этой сессии.

Первоначальные ошибки собственной оснастки сохранены: CRC-fixture ошибочно
учитывал 67 вместо 64 бит; selector-мутант доходил до NULL callback раньше
проверки; статическая аннотация использовала PC предыдущей инструкции.
Исправлена только новая оснастка/аннотация. Рабочий runtime не менялся после
первого успешного запуска. Итоговые прогоны не подменяют историю неудачных.

## Интеграция после PR114 (2026-10-03)

Числа выше относятся к сохранённым испытаниям пакета от 2026-10-02, а не к новым
GitHub Actions. Новый кандидат основан на PR114
`c415cd5b4ec804f310bd99e89010def41c80417b` и требует отдельных результатов CI
для своего точного commit/tree. Все новые испытания выполняются только в GitHub
Actions; исходный ELF остаётся данными и не запускается.

На этой базе `chip1368.c` уже включает L14 drive-strength. Единственная
совместимость в `verify.py` вызывает существующий `address_bm1368_bytes`:
он требует точные 14347 байт L14 (SHA-256
`d31a47e24504be3cf48cad8cbca96a9a38f08fd5aa0b0a27e672fac84bff5ce6`), проверяет
отдельный gated append и возвращает неизменённые 11280 байт L13 (SHA-256
`91cfb6f3bb640bcf3519027243970bcb37aeeb0275f96b931dd17cab940540d2`).
Исходный L13 pin проверяется до перехода и повторно по полученным байтам.
Старый L13 файл, изменённый L14, перенесённый путь, executable-файл и symlink
не принимаются. Остальные 21 source pin сохраняют свои SHA-256 проверки.
`static-witness.json`, `original-code.asm`, runtime-исходники L15 и все файлы базы
остаются неизменёнными; второе ядро и новая production-проводка не добавляются.

Отдельные caller-контроли проверяют настоящий `verify(root, False)` с временными
source roots, включая неверные старые pins, старый/current источник, prefix/suffix
drift, независимый SHA-256 возвращённых байтов, обычные зависимости и типы путей.
Они запускаются с Python и `-O`, как и существующие shared-pin контроли. Workflow
отслеживает все witness/build входы, reference, shared helper, его зависимости,
новые тесты и собственную конфигурацию. Host-сценарии, 21 семантический контроль
и ASan/UBSan собирают только семь явно указанных host TU с GCC и Clang.
Дальнейший раздел о L14 сохранён как исторический план пакета: L14 уже входит
в выбранную базу. Полноценный T21 runtime и работа с аппаратурой этим не доказаны.
