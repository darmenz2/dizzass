## Сохранённое поведение

**Три обычных формата — 9, 10, 11 байт с преамбулой `AA 55`.** Перед выбором
используются два различных внутренних селектора, платы и чипа:

```
variant = 0                                  при board == 0
variant = 0                                  при chip == 6 и board == 4
variant = 1                                  при остальных board и chip == 7
variant = 2                                  иначе
обычный размер кадра = 9 + variant
специальный режим: 9 байт, всегда ответ регистра
```

Числа селекторов **не отождествляются с названиями ASIC-моделей**. Смысл отдельного
флага, включающего специальный режим, пока не назван точнее. Проверяется стабильная
конфигурация: изменение флага во время работы оригинального потока не моделируется.

Оригинал сначала ждёт полного минимального размера, даже если первый байт уже
является мусором. После этого плохой первый байт отбрасывает один байт; `AA` с
неверным вторым байтом — два. Поэтому `AA AA 55` не даёт скользящего повторного
поиска от второго `AA`. Это поведение сохранено, не «улучшено» молча.

В обычных форматах бит 7 последнего байта выбирает nonce-ветвь. Иначе декодируются
ответ регистра, 32-битное значение big-endian, два адресных байта и младшие пять
бит последнего байта. Формат variant=1 сдвигает начало значения на один байт;
variant=2 не использует два промежуточных байта для значения регистра.

**Пять извлечённых бит — не проверенный CRC.** На восстановленной границе CRC
не проверяется. Это не вывод об отсутствии проверки в прошивке вообще: последующая
обработка пока не восстановлена полностью.

Селекторы chip=0..4 исключают ответ регистра `0x40` из очереди в исследованной
ветви. Остальные значения дают `UINT32_MAX`, не совпадающий с байтовым адресом.
Это фильтр регистра, **не проверка контрольной суммы**. Отфильтрованный кадр уже
потреблён из входного потока.

Для nonce восстановлено только извлечение 5-битного индекса 0..31. Возврат
`VN135_RX_NONCE_RAW` не означает, что задание существует, nonce корректен или
пул принял шару. Работа с таблицей заданий, версиями, вычислением хеша и отправкой
результата не реализована этим этапом.

## Новый потоковый адаптер — отдельно от оригинального кода

`reconstruction/support/work_rx_stream.c` — новый bounded-адаптер, не исходный
кольцевой буфер VNish. Держит максимум 11 байт, принимает фрагменты, возвращает
не более одного события за вызов и явно сообщает число принятых входных байтов.
Остальные байты входного фрагмента вызывающий код обязан передать следующими
вызовами. Нет выделений памяти, скрытых переподключений, потоков и UART-команд.

`message.consumed` — число байтов, удалённых из накопленного буфера;
`input_consumed` — сколько байтов принято из текущего вызова. Это разные величины.
Существующий UART-код не заменён; новый адаптер не включается на устройствах сам.

Все новые 6 088 случаев повторены на GCC и Clang; повтор не прибавляет уникальных

Нативные C-тесты защит и фрагментации: 3 600 потоковых прогонов. ASan/UBSan
проверяют именно native-набор, не все Python/ctypes сравнения. Новый ограниченный
ARM-интерпретатор расширен только инструкциями REV/LDRSB: 2 053 синтетических
проверки добавления, отдельно от 1 318 проверок предыдущего расширения.

В эталонном сравнении реально интерпретируются оригинальные кольцевые операции
`0xd1df0`, `0xd1f20`, `0xd20ac`, включая переход через конец буфера. Их результата
не подменяют ожидаемым кадром. Подменены memcpy, mutex-unlock, чтение селекторов
и последняя постановка ответа в очередь. Сам цикл потоков и их конкурентность
не эмулируются. CRC/проверка nonce/оборудование этими тестами не подтверждены.

## Проверка с ядром Linux

`tests/test_work_rx_linux_pty.c` создаёт собственную пару PTY и связывает:

```
ядро Linux → восстановленный UART-read → новый адаптер → разбор регистра
```

88 сообщений прошли фрагментацию от 1 до 11 байт, передачу двух кадров подряд,
обычные форматы и специальный режим, обычные и sanitizer-сборки GCC/Clang.
Это реальная работа с Linux-псевдотерминалом, но **не физический UART, скорость
провода, питание или ответ ASIC-чипа**.

## Структура, сборка и ограничения

Теперь частично восстановлены 6 из 46 наблюдаемых исходных файлов, 40 исключены
из сборки. Библиотека содержит 8 C-единиц трансляции: 6 наблюдаемых файлов и два
отдельно обозначенных helper/adapter файла. Это не процент готовности.

```sh
make -f Makefile.recovery clean
make -f Makefile.recovery all test arm evidence-check sanitize
make -f Makefile.recovery linux-pty sanitize-linux-pty
make -f Makefile.recovery linux-pty-rx sanitize-linux-pty-rx
python3 tests/test_assembler.py
python3 tools/update_overlay_inventory.py --check
```

Выход — host/ARMv7 `.a`, не executable cgminer. ARM freestanding без Linux
sysroot. `full-runtime` по-прежнему возвращает ошибку. Сборщик overlay сохранён,
публичный cgminer целиком не включён и его совместная сборка не заявляется.

Привязка T21 к конкретному драйверу остаётся неподтверждённой. Далее требуются
инициализация цепей, проверка ответов и nonce с живыми заданиями, реальный
аппаратный обмен, PSU/датчики/защиты, API драйвера cgminer и автотюн.

Листинги, границы и SHA-256: `evidence/stage6/`. Протоколы новых GCC/Clang-проверок:
`evidence/validation/stage6/`. Окончательная проверка распакованного ZIP поставляется
отдельным логом и JSON; `tools/verify_stage6.py` воспроизводит её группами.

**Ничего из этого не установлено на ASIC. Штатный cgminer не заменять.**
