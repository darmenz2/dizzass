# A-08 — настройка температурных датчиков одной цепи, `0x58b50`

Задача #30, координация #2. Независимая база:
`12446bed78a060a49364a80bcbfb4340b13f4f27`, дерево
`2e73cb80b2ccbb15d24d9a7deb3c51f65bcd23ac`.
Непринятые PR не включены, общая ветка не меняется.

## Восстановление и переиспользование

`vn135_chain_temperature_setup_135` переносит управляющее тело `58b50..58cec`.
Оригинальный путь `/tmp/build/src/backend/chain.c` подтверждён указателем
диагностики и XOR-декодированием литерала. Проектный файл
`src/backend/chain-temperature-setup.c` выделен для отдельной офлайн-сборки;
его имя не выдаётся за имя исходного файла производителя.

Нижняя `b7798` УЖЕ представлена функцией `vn135_temperature_initialize` в
`src/backend/temp.c`. Новый маленький адаптер
`vn135_chain_sensor_initialize_existing_135` вызывает именно её. Старый код
не менялся. Это не `b5d90`/`vn135_temperature_initialize_direct_135`: у той
другие допустимые виды датчиков и синхронное чтение. Подмена одной функции
другой только по похожему имени была бы ошибкой.

Использованы существующие `vn135_route_chain`, `vn135_temperature_sensor`,
`vn135_general_monitor` и `vn135_general_model`. Новый view связывает цепь с
её backend явно; он не накладывается приведением типов на vendor ABI.
Обычный cgminer `driver-bitmain.c` не имеет контракта этого координатора;
ядро, сетевой стек, CRC, UART и второй алгоритм инициализации не добавлялись.

## Точное поведение

1. Разрешить модель через backend перед проверкой присутствия цепи. Если цепь
   отсутствует либо её unsigned state — 3, 4 или 5, вернуть 0. При этих ранних
   выходах количество датчиков и массив не читаются. Модель может быть NULL,
   когда выход предотвращает её разыменование; сам backend должен существовать.
2. Один раз прочитать знаковое количество из модели. Нулевое/отрицательное
   количество даёт 0 без нижних вызовов. `chain.sensor_count` НЕ используется.
3. Для каждой исходно посчитанной позиции заново загрузить массив датчиков.
   Пропустить `access_kind` 0 и 3, а также 4 при нулевом `skip_initial_read`
   (исходный byte+51). Состояние самого датчика здесь не является фильтром.
4. Вызвать `b7798` для выбранного датчика. При нуле продолжить цикл.
5. При любом ненулевом результате вывести сообщение строки 1208, severity 2:
   `chain#%d sen#%d - failed to init`. Номера читаются после инициализатора,
   увеличиваются на 1 с 32-битным переполнением.
6. ПОСЛЕ сообщения записать state=3 в тот же захваченный объект датчика.
   При mode==2 вернуть -1. Иначе прочитать его текущую role: при role==2
   вернуть -1, при других значениях продолжить.
7. Завершение всего цикла возвращает 0 даже после некоторых ошибок.

Последствия: лог может видеть состояние до внешней записи 3; у нижнего
инициализатора бывают собственные записи state=3, поэтому обещания «лог всегда
видит 2» нет. Callback логирования может изменить role до её проверки.
Замена массива внутри callback не меняет адрес текущего датчика, но влияет на
следующую итерацию. Изменение количества или модели не сокращает уже начатый
цикл; новый самостоятельный вызов прочитает актуальное количество.

Режим — полное uint32_t, не байт: 258 не равен 2. Установка role=2 сама по себе
не вызывает отказ, пока нижний инициализатор вернул 0. Дополнительных повторов,
проверок присутствия в каждой итерации, rollback или регистрации ответа нет.
В частности, kind4 с ненулевым byte51 достигает старой b7798 и получает её
исходный отказ на неподдерживаемом виде; новый «успешный» путь не придуман.

## Границы интерфейсов

У самого координатора callbacks явно заданы. Прямой набор допускает
последовательные изменения модели, массива и скалярных полей в этих точках.
View/backend/chain и захваченные датчики остаются живы; каждый положительный
начальный count должен помещаться во все достигнутые массивы.

У адаптера существующего b7798 контракт УЖЕ: идентичности, описания датчика,
индекс цепи и таблица операций стабильны, меняются только предусмотренные
выходы нижних операций. Вложенные проверки используют этот ограниченный
домен; прямые мутации координатора не объявляются проверкой произвольных
изменений внутри старого инициализатора. Никаких скрытых операций устройства.

Нулевой return не доказывает работоспособность датчиков или наличие цепи.
Нижняя настройка/чтение/запись регистров, время и диагностика моделируются.
Нет live mutex, конкуренции, реальной калибровки, GPIO/UART или аппаратного ACK.

## Проверки

- **1 024** прямых сценария / **3 213** событий: исполняется вся исходная 58b50
  и getter модели; нижний инициализатор и лог — явные scripted-эффекты.
- **171** вложенный сценарий / **2 576** событий: исполняются исходные
  `58b50 -> b7798`, а C использует новый координатор и реальную прежнюю
  `vn135_temperature_initialize`. Проверяются ID, ошибки и повторы чтения,
  настройка remote, неподдерживаемые виды и промежуточные состояния.
- Всего **1 195 сценариев / 5 789 событий / 212 313 ARM-шагов**, 475 посещённых
  адресов инструкций. В события входят снимки полей/обеих банков датчиков;
  сравниваются также итоговые состояния и неизменность непричастных байтов.
- **1 052** нативных сценария / **64 393** проверки: байтовые инварианты,
  защитные границы, пропуск NULL на недостижимых путях, повторные вызовы,
  переключение банков/модели и настоящий старый инициализатор.
- **15** отдельно скомпилированных семантических мутаций должны отвергаться
  оригинальным oracle. Для них используются **17** различающих входов,
  прошедших на baseline, а не все 1 195 сценариев для каждого мутанта.
  Сбой сборки, сигнал, таймаут или исключение без SEMANTIC_MISMATCH не PASS.

GCC/Clang используют разные каталоги. Нативные тесты повторяются с ASan/UBSan,
статический анализ — отдельно. Прежние thermal-sensors и thermal-routes
проверяются без изменения. Evidence содержит дизассемблирование 58b50,
хеши оригинальных диапазонов, строки/указатели и 22 неизменённых зависимости.
Интерпретатор не расширен новыми инструкциями.

Промежуточные агрегированные локальные команды дважды прерывались лимитом
времени инструмента: общий запуск компиляторов и первый запуск thermal-routes.
Эти неполные запуски сохранены в логах, не считаются PASS. Проверки повторяются
отдельными завершёнными заданиями, без отключения санитайзеров/старых тестов.
Итоги фактических команд и отдельной чистой копии — в логах этапа; результат CI
проверяется по SHA PR, не выводится из наличия workflow.

```sh
make -f integration/chain-temperature-setup-135.mk CC=gcc CHAINSET135_DIR=build/a08-gcc dizzass-chainset135-original dizzass-chainset135-test dizzass-chainset135-negative
make -f integration/chain-temperature-setup-135.mk CC=gcc SANITIZE=1 CHAINSET135_DIR=build/a08-gcc-san dizzass-chainset135-test
# Для Clang заменить CC и использовать другие каталоги.
```
