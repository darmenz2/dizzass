# 0x57a10 — применение частоты цепи и обновление сохранённых значений

База: `174fcc64acd17878b4fd6dfba73b33a6c2dacf42`, дерево
`e9031d8f9b6112d2486756fb3130252d7fb426ef`. Продолжение опубликованной
рабочей функции `65fcc`; старые патчи повторно не применяются.

## Реализация и повторное использование

Восстановлено управляющее тело `57a10..57d34`. Исходный модуль подтверждается
литералом `/tmp/build/src/backend/chain.c`. Новый проектный файл
`src/backend/chain-frequency.c` выделен только для изолированной офлайн-сборки;
это не утверждение о таком имени файла производителя. Старые `chain.c`,
`base.c`, `frequency-worker.c`, типы и интерпретатор сохранены побайтно.

`vn135_chain_set_frequency_135` использует уже существующие
`vn135_general_chain`, `vn135_route_chain`, `vn135_route_chip`. Дополнительный
view хранит только идентичность цепи и владельца двух методов backend.
Нет второго майнера, PLL-реализации, сетевого стека или production-заглушек.
Просмотрен существующий `driver-bitmain.c`: его сериализатор конфигурации
Bitmain не эквивалентен этому контракту методов и обновлению per-chip cache.
Он не изменён и не используется как неподтверждённая замена.

## Исходная последовательность

1. Получить владельца методов из chain+1c. Для отсутствующей цепи и состояний
   3, 4, 5 — вернуть 0 без вызовов. Остальные состояния сохраняют исходный
   unsigned-предикат, а не заменяются проверкой только состояния 2.
2. Вызвать метод backend+140 с подструктурой chain+2b8 и первоначальным double
   частоты. Дробная часть здесь НЕ отбрасывается. При ненулевом результате —
   диагностика строки 1060 и возврат -1, без новых записей cache и блокировки.
3. Вызвать блокировку `5a6108(chain)`. Её результат игнорируется оригиналом.
   Прочитать количество чипов и массив ПОСЛЕ этого вызова.
4. Записать в chip+8 каждого чипа результат исходной `VCVT.s32.f64`: усечение
   к нулю с насыщением знакового int32 для конечных значений. Например, нижний
   метод получает 635.75, а сохранённое значение чипа становится 635.
5. Рассчитать минимум, среднее и максимум по этим записям. Поля цепи:
   минимум +28, среднее double +30/+34, максимум +38. При нулевом количестве
   все три результата нулевые, чтения массива нет. Затем unlock `5a66c4`.
6. Снова получить владельца методов — ДО вызова `fdfbc`. Только при результате
   platform=4 выполнить метод backend+188 (pulse width). Сам указатель метода
   берётся ПОСЛЕ platform, из ранее сохранённого владельца. Тесты различают
   замену владельца и замену его метода на этой границе.
7. Аргументы pulse width: исходный word_10, word_20, константа 1. Если
   перечитанный минимум цепи строго меньше 450, вместо word_20 передаётся 4.
   Ровно 450 не включает эту подстановку. При ошибке — строка 1074 и -1;
   иначе 0. Нового rollback нет.

**Ошибка pulse width случается после записи cache.** Её нельзя представить
как отсутствие изменений всей функции. Нет повторной проверки present/state
после успешного первого метода: изменения этих полей в callback не добавляют
новой отмены. Отрицательный результат lock/unlock также не создаёт новых
ветвей. Это восстановленное поведение, не рекомендация для аппаратного API.

## Представления полей и границы

Для этого view source chain+8c представлен `general.detected_8c`; существующий
`thermal.chip_count` повторно не читается. При production-интеграции эти две
исторические проекции одного исходного поля нельзя вести независимо: требуется
единый источник количества. Тест специально проверяет, что новое тело не
начинает читать второй, не объявленный его контрактом счётчик.

Массив использует `thermal.chips`; исходное chip+8 — `word_08`. Четыре
`cleared_words` представляют +28/+30/+34/+38; среднее сохраняется через его
IEEE binary64 биты, без указательного aliasing. Это не vendor ABI.

Входные частоты конечны. Положительное количество не превышает выделенный
массив, отрицательное количество вне принятого контракта. Объекты раздельны,
их память стабильна; callback последовательны и завершаются. Конкурентные
изменения полей между инструкциями, отрицательные/повреждённые размеры, NaN,
Inf, нестандартный FPSCR и отмена внутри mutex не заявляются проверенными.

Нижние методы +140/+188 и библиотечные эффекты остаются явными callback.
Сборки и тесты не обращаются к ASIC, не устанавливают частоту и не запускают
настоящие потоки. Возврат 0 также возможен для пропущенной цепи и не является
подтверждением аппаратного применения.

## Проверки

Прямой oracle исполняет неизменённые инструкции `57a10`, включая исходные
непрозрачные арифметические условия. Используется прежний ARM32Difficulty;
новых opcode и изменений старых тестов нет.

- 919 сценариев, 3 641 сравниваемое событие, 138 599 шагов исходных инструкций;
  сравниваются результаты, порядок/аргументы вызовов, состояния на границах
  и после возврата. Проверяются дополнительные записи вне разрешённых полей.
- 4 161 нативный сценарий, 94 741 проверка; включая 168 последовательных
  связок `65fcc -> 57a10` и ошибки обоих методов с прежней `60a2c`.
  Нижние аппаратные эффекты и остановка цепи в этой связке моделируются явно.
- Восемь отдельно скомпилированных неверных вариантов должны отвергаться
  несовпадением с оригиналом: неверный state gate, потерянная ошибка, раннее
  чтение количества, неправильное округление, включительная граница 450,
  перестановка параметров, позднее чтение владельца и потеря среднего.
  Ошибка сборки или произвольное падение не считаются успешным обнаружением.
- GCC/Clang, ASan/UBSan, статический анализ; предыдущие worker/fall/handlers/
  mining-stop выполняются отдельными регрессионными целями.

Составная C-проверка не является исполнением всего вложенного vendor-runtime
одним оригинальным процессом. Прямой oracle новой функции и предыдущий oracle
worker проверяются раздельно. Результат CI следует смотреть по SHA коммита;
появление workflow само по себе не означает PASS.

## Разрешение следующего адреса

Повторно исполнен существующий ограниченный выбор таблицы `d21dc -> e1450`
для chip-selector=4 (BM1368), пяти значений платформы и трёх подтипов: 15 случаев.
При размещении таблицы на backend+110 получены:

- backend+140 (table+30): `0xe249c` — следующий нижний метод установки частоты;
- backend+188 (table+78): `0xe34cc` — нижний метод pulse width.

Тела этих двух методов здесь не перенесены. Chip-selector=4 и platform=4 —
РАЗНЫЕ параметры, их нельзя смешивать или считать доказательством физической
платы T21. Отдельная привязка модели к железу остаётся необходимой.

Проблема времени жизни аргументов родителя `65b3c` этим этапом не изменяется.
Производственные `cgminer.c`, `Makefile.am`, старые функции, reference ELF,
история upstream и ограничение 32 слотов сохранены.
