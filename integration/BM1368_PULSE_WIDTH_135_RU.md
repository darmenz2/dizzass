# BM1368: ширина импульса и задержка — 0xe34cc

База: `6ba87a19d83d024453d725aab91c071cbacdf274`, дерево
`d7985e09361cf61bfd741a925c32ec362295923b`. Предыдущие этапы уже опубликованы;
их патчи повторно не применяются.

## Восстановленный участок

`vn135_bm1368_set_pulse_width_135` воспроизводит управляющее тело
`e34cc..e35a0`, литералы до `e35b4`. Исходный модуль подтверждён строкой
`/tmp/build/libbitmain/src/chip/chip1368.c`. Проектный файл
`libbitmain/src/chip/chip1368-pulse-width.c` выделен для офлайн-сборки;
это не заявление о таком имени файла производителя.

Существующие device-view, `vn135_bm1368_write_register_135`, encoder/CRC,
кэш, диспетчер, AML и UART переиспользованы. Узкий адаптер
`vn135_bm1368_pulse_register_135` связывает новый вызов с уже восстановленной
записью регистра. Нового UART, PLL, CRC или второго майнера нет.

Ранее `dizzass_bm1368_reset_cores` уже использовал сходное слово регистра.
Его нельзя вызывать вместо e34cc: это многошаговый сброс с другими записями,
ожиданиями, чтениями кэша и проверками диапазона. Простая упаковка битовых
полей перенесена отдельно, старый reset-алгоритм не изменялся.
Штатный `driver-bitmain.c` также не реализует данный контракт метода.

## Точное поведение

1. Собрать слово беззнаковыми операциями:

```c
0x80008000u | ((pulse_width & 3u) << 6) | ((clock_delay & 7u) << 3)
```

Используются только младшие 2 и 3 бита входов соответственно. Например,
width=5 эквивалентен width=1, delay=8 эквивалентен delay=0 на этой границе.
Это воспроизведение масок оригинала, не рекомендация значений для оборудования.
Дополнительных проверок диапазона не добавлено.

2. Четвёртый исходный ARM-аргумент r3 не влияет на результат: инструкция
`e34e8` заменяет его регистром `0x3c` до какого-либо чтения. В типизированном
API аргумент оставлен как `ignored_4` для явной связи с родительским методом.
Единица, передаваемая родителем, здесь НЕ становится переключателем режима.

3. Один раз вызвать `e4a74(device, 1, NULL, 0x3c, word)` — широковещательную
запись с нулевым chip. В отличие от метода PLL e249c, второго вызова нет.
Нет предварительного чтения кэша, дополнительной задержки, повтора или отката.

4. При нулевом результате вернуть 0. При любом ненулевом — последовательно
вывести два сообщения severity 1 и вернуть -1:

- строка 387: `chain#%d - failed to send core command`;
- строка 569: `chain#%d - failed to set CLOCK_DELAY_CTRL`.

Перед КАЖДЫМ сообщением device+18 читается заново и увеличивается на 1
с 32-битным беззнаковым переполнением. Обработчик первого сообщения может
изменить индекс для второго. Замена этой последовательности одним сообщением
или одним ранним снимком индекса не соответствует оригиналу.

## Связка с существующими слоями

Вложенный oracle исполняет исходные ARM-тела:

`e34cc -> e4a74 -> d26ac -> 117f7c -> 10e6c0`, вместе с CRC и `107648`.

C использует соответствующие восстановленные функции и существующий кэш.
На границе системной записи сравнивается полный 11-байтный кадр, включая
префикс и CRC. Проверяются два уровня блокировки, выделение/освобождение
временного буфера, исходные повторы UART и обновление общего кэша цепи.

Ошибка кэша возможна ПОСЛЕ успешной передачи нижнему слою: e34cc всё равно
выводит оба сообщения и возвращает -1. Поэтому текст `failed to send` сам
по себе не устанавливает отсутствие передачи или её аппаратную причину.
При ошибке send ниже дополнительно возникает сообщение register-write
строки 350; оно не заменяет два сообщения e34cc.

В нативной связке с родительской `57a10` проверены граница 450, замена delay
на 4 ниже неё, передача width и неиспользуемого четвёртого аргумента, пропуск
pulse-метода на других платформах и ошибка после обновления частот чипов.
Первый метод установки самой частоты в ЭТОМ родительском fixture явно задан
callback; его реальные PLL-проверки остаются в предыдущем отдельном наборе.
Выбор платформы родителя и принудительное AML-binding теста не доказывают
физического соответствия одной плате T21.

## Проверки и их границы

- Прямой oracle: **2 502 сценария / 6 989 событий**, **126 294 шага** исходных
  инструкций. Все байтовые значения обоих параметров, все 32 младших сочетания,
  однобитовые и случайные полные слова, разные статусы, необязательный logger,
  повторные вызовы и изменения индекса между callback.
- Вложенная отправка/кэш: **251 сценарий / 3 807 событий**, **484 652 шага**.
  Проверяются точные состояния и полные таблицы, граничные ошибки UART,
  отсутствие памяти, отключение кэша и мутации устройства. Всего двух групп:
  **2 753 сценария / 10 796 событий**, **610 946 шагов**, 532 адреса инструкций.
- Нативный набор: **28 362 сценария / 1 191 092 проверки**, включая
  **168 родительских композиций** и отдельный повторный вход. Большая часть
  количества — регулярные переборы масок и проверка неизменности таблиц;
  эти числа не означают миллионы независимых аппаратных состояний.
- **12 семантических мутаций** должны собраться и быть отвергнуты именно
  сравнением с оригиналом, а не сбоем компиляции или таймаутом.

GCC и Clang собираются в разных каталогах; нативные цели повторяются с
ASan/UBSan. Старые transport-dispatch, register-write и chain-frequency
выполняются отдельно. Контрольные суммы прежних библиотек, кода и тестов
закреплены без пересчёта под новые тела. Общий ARM-интерпретатор не изменён,
новых opcode нет. Результаты команд — в логе этапа; CI проверяется по SHA.

Таблицы/объекты валидны и стабильны, callback последовательны и завершаются.
Системные write/memcpy/errno/mutex/malloc/free/delay моделируются. Внутренние
сообщения старых UART/cache API учитываются отдельно, но не входят в сравнение;
диагностика e34cc и e4a74 сравнивается. Полное равенство всех логов процесса,
реальные гонки/потоки, ответы чипа и аппаратная приёмка не заявляются.

## Продолжение

Оба выбранных нижних метода родительской установки частоты теперь имеют
офлайн-реализации. Следующий отдельный неразобранный узел остановки — `b8e54`,
вызванный из `663cc` до задержки и диспетчера снижения частоты. Его назначение
нужно установить по инструкциям; новое имя/поведение пока не приписывается.

Безопасное владение аргументами `65b3c`, исправление коротких UART-записей для
production, RX и аппаратная привязка остаются отдельными задачами. Старые
исходники, cgminer.c, Makefile.am, device_drv, лимит 32 слотов, пулы/devfee,
частоты и напряжения устройств не менялись. Команды ASIC не отправлялись.
