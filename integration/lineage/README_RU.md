# Кандидат исходной базы по маркеру 9f9b64d5

## Находка и границы доказательства

В исходном образе VNish T21 1.3.5, внутри `uramdisk.image.gz` → `etc/components.json`,
поле `cgminer_btm` равно `9f9b64d5`, а `cgminer_btm/libbitmain` равно `1a52239`.
Хеши исходного архива и извлечённого манифеста записаны в `candidate.json`.

Прямой запрос к публичному `ckolivas/cgminer` разрешил первый префикс в:

```
9f9b64d5abddad481c7a64c9c5668e2da9d882ef
```

Это merge от 22 июня 2017 года. `configure.ac` задаёт версию **4.10.0**.
Два родителя — `31047bd95c0f794fc7ad4e803a86e7e404e0ca75` и
`9de831350aa5d439082163512bcef8b5c4daec98`; второй содержит `Fix testnet diff`.
Относительно первого изменён нижний предел `powdiff` в `set_blockdiff`: 8 → 0.

Это существенно более сильный ориентир, чем сходство имён функций, но **не
доказательство идентичности публичного дерева закрытому cgminer VNish**.
В манифесте только восемь символов, не полный SHA. Маркер мог сохраняться после
приватных изменений; точный vendor ancestor и цепочка таких изменений неизвестны.
Компонент `libbitmain` по `1a52239` пока не разрешён в проверенный публичный объект.
Отсутствие результата поиска не доказывает, что исходники нигде не опубликованы.

## Что сохраняем

`upstream/candidate-9f9b64d5` предназначена для **оригинального Git-объекта и его
истории**, не нового коммита с похожими файлами. Workflow сначала проверяет SHA,
дерево, родителей и два исходных blob. Он создаёт только эту отдельную ветку;
если она уже указывает на другой commit, работа прекращается.

Создание ветки через REST по чужому SHA не сработало: объект ещё отсутствовал
в скопированном приватном репозитории. Поэтому workflow получает публичные объекты
через Git fetch с историей и передаёт их обычным push, без force.
**Пока workflow не подтвердил LINEAGE_CANDIDATE_PRESERVED, импорт не завершён.**

Рабочая база 4.11.1 `b8491c66e7e22f23a9edf095dd1337ee581e88bd` не меняется.
Новый кандидат полезен для сравнения и поиска изменений; он не повод откатывать
исправления или заменять проверенные native-интерфейсы более старым ядром.
`main`, `upstream/ckolivas`, корневые `cgminer.c`, `miner.h`, `Makefile.am` и
восстановленные аппаратные модули эта работа не заменяет.

## Воспроизводимая проверка

Скрипт `audit.py` читает Git-объекты, но не запускает код кандидата. Отчёт содержит
merge-base, число отличающихся коммитов, число исходных путей, поиск путей
`libbitmain` и сравнение двенадцати функций ядра.

`same_tokens` означает совпадение списка лексических токенов от имени функции
до конца тела после удаления комментариев и пробельного оформления. Это **не
проверка машинного кода или эквивалентности поведения**: тип возвращаемого
значения, заголовки, макросы, параметры сборки и вызываемые функции не сравниваются.
Разбор не является полным C-preprocessor; неоднозначные определения отклоняются.
`different_tokens` требует изучения diff, а не автоматической замены функции.

```
python3 -m unittest discover -s integration/lineage -p test_audit.py -v
python3 integration/lineage/audit.py --repo /path/to/public-cgminer.git --output /tmp/lineage-audit.json
```

Workflow `cgminer-lineage.yml` выполняет обе проверки и сохраняет кандидат.
Успешный аудит происхождения не означает успешную сборку или майнинг на T21.
Аппаратный выбор формата TX86/TX88, безопасный повтор слотов, PSU, защиты и
автотюн остаются отдельными незакрытыми задачами.
