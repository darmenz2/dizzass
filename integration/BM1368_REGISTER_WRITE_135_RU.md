# BM1368: запись конфигурационного регистра — 0xe4a74

База: `3395ab351b811aee4fe8142dec6043d84abc72ba`, дерево
`a56a0e97b0622721264d2c66f3b0d6846e33e7af`. Продолжение `e249c`.

## Перенос и повторное использование

`vn135_bm1368_write_register_135` воспроизводит управляющее тело
`e4a74..e4bec` (литералы до `e4c04`) из исходного
`libbitmain/src/chip/chip1368.c`. Новый проектный файл
`libbitmain/src/chip/chip1368-register-write.c` выделен для офлайн-сборки;
это не утверждение о таком имени исходного файла производителя.

Использованы прежние `dizzass_bm1368_command_encode`, `vn135_crc5_bits`,
`vn135_chip_reference`, device-view предыдущего этапа и функции
`vn135_reg_cache_set_chain` / `vn135_reg_cache_set_chip`.
Два узких адаптера подключают существующий caller-owned cache к новому
интерфейсу. Второй кэш, CRC или реализация поиска регистра не создаются.

Просмотрен `vn135_bm1398_set_config`: формат пакета и выбор кэша совпадают,
но его API принимает индекс цепи ПО ЗНАЧЕНИЮ до send и не воспроизводит
диагностику данной функции. Поэтому он не используется как полная замена
`e4a74`, читающей индекс после транспорта. Его код не изменён.
Штатный `driver-bitmain.c` формирует другой TXCONFIG-токен и также не является
эквивалентной заменой этого метода. Производственный cgminer не меняется.

## Порядок оригинала

1. Взять wire-address из chip+4; при NULL chip использовать 0.
   В команду помещается младший байт адреса и регистра, value — big-endian.
2. В header включить broadcast ТОЛЬКО при `mode == 1`. Остальные 32-битные
   значения mode формируют unicast-header. CRC считается по 64 битам.
3. Один раз вызвать `d26ac(device, payload, 9)`.
   Передаётся девятибайтное тело БЕЗ префикса `55 aa`.
4. При любом ненулевом статусе send — сообщение строки 350, severity 1,
   `chain#%d - failed to send SET_CONFIG command`, затем -1. Индекс устройства
   для сообщения читается ПОСЛЕ send, к нему прибавляется 1 беззнаково.
   Кэш при этом не вызывается.
5. При нулевом send заново прочитать device+18. Если `mode != 0`, вызвать
   `107648(index, reg, value)` — обновление общего кэша и чипов цепи.
   Если mode нулевой, вызвать `107ed0(index, chip_index, reg, value)`;
   chip_index берётся из chip+0 ПОСЛЕ send, при NULL chip используется 0.
6. Вернуть 0 при нулевом статусе кэша; любое другое значение преобразовать в -1.
   Внешнего сообщения об ошибке кэша эта функция не добавляет.

Проверки mode для wire и кэша **различаются**. Например, mode=2 даёт unicast
на проводе, но обновление всех записей цепи в кэше. Этот режим не рекомендуется
для реального устройства; здесь фиксируется исходная семантика.

Полный 32-битный reg сохраняется для кэша. Поэтому reg=0x108 даёт wire-byte 8,
но кэш получает 0x108 и отклоняет его. Аналогично некорректный индекс/выключенный
кэш обнаруживаются ПОСЛЕ передачи команды. Возврат -1 не означает отсутствия
отправки; автоматическое повторение или откат не добавлены.

Нормализация входов для прежнего строгого encoder выполняется только на его
границе: `mode==1`, `address&255`, `reg&255`. Для таких аргументов и локального
буфера в 11 байт encoder всегда успешен. Защитный выход при ошибке encoder
недостижим в принятой области и не объявляется новым поведением оригинала.
Первые два байта результата encoder не передаются в d26ac: префикс добавляет
нижний платформенный слой. Указатель payload действителен только во время
синхронного callback и не может сохраняться им для отложенного чтения.

## Кэш и границы наблюдения

`107648` обновляет общий слот и ТОТ ЖЕ номер слота во всех чипах, без отдельного
поиска адреса в каждом чипе. `107ed0` изменяет только выбранный чип.
Проверены разные значения записей, перестановка слотов чипов и повторяющиеся
адреса. Эти алгоритмы уже были восстановлены и переиспользованы без изменений.

Внутренние диагностические сообщения старых cache/PLL API исторически опущены.
Новый oracle исполняет их исходные инструкции, считает такие сообщения отдельно,
но исключает из сопоставляемого trace. Диагностика самой `e4a74` и родительской
`e249c` сравнивается. Полное совпадение всех логов процесса не заявляется.

## Проверки

- Прямой oracle: **1 154 сценария, 2 405 событий**. Исходные `e4a74` и CRC
  против нового тела с явно заданными статусами кэша/транспорта. Все байтовые
  значения mode/адреса/регистра, полные слова, ошибки, NULL chip, мутации индексов
  после send, повторные вызовы и необязательный logger.
- Вложенный кэш: **430 сценариев, 1 554 события**. Исполняются исходные
  `107648/107ed0`, не успешные заглушки. Сравниваются все таблицы, количество,
  флаг доступности, события и состояния на границах; проверяются лишние записи.
- Вложенная установка PLL: **48 сценариев, 188 событий**. Одна модель исполняет
  исходные `e249c -> ff288 -> e4a74 -> CRC/cache`, а C использует существующий
  solver и кэш. Транспорт остаётся callback. Проверены отказы первой/второй
  отправки и отключение кэша между ними.
- Всего: **1 632 сценария, 4 147 событий, 3 801 216 интерпретированных шагов**,
  845 посещённых адресов инструкций. Внутренние исключённые сообщения считаются
  отдельно в original.json. ARM-интерпретатор не расширялся и не менялся.
- Нативный набор: **2 360 сценариев, 64 853 проверки**, включая защитные поля,
  точное состояние таблиц, повторный вход, необязательные недостижимые callbacks
  и **168 связок PLL -> register-write -> настоящий восстановленный кэш**.
- **10 семантических мутаций** должны собраться и быть отвергнуты именно
  несовпадением с оригиналом: неверные mode-тесты, префикс в payload, старые
  индексы, усечение reg для кэша, потеря ошибок, неверный NULL-index и диагностика.

GCC/Clang используют разные каталоги; нативные цели повторяются с ASan/UBSan.
Старые PLL, chain, worker и encoder проверяются отдельными регрессиями.
Результаты выполненных команд находятся в логе этапа; удалённый CI проверяется
по SHA опубликованного коммита, не предполагается из наличия workflow.

```sh
make -f integration/bm1368-register-write-135.mk CC=gcc dizzass-reg1368-original dizzass-reg1368-test dizzass-reg1368-negative
make -f integration/bm1368-register-write-135.mk CC=gcc SANITIZE=1 dizzass-reg1368-test
make -f integration/bm1368-register-write-135.mk CC=clang REG1368_DIR=build/register-clang dizzass-reg1368-original dizzass-reg1368-test dizzass-reg1368-negative
make -f integration/bm1368-register-write-135.mk CC=clang SANITIZE=1 REG1368_DIR=build/register-clang-san dizzass-reg1368-test
```

## Оставшийся участок

Следующий узел — `0xd26ac`, диспетчер транспорта. По сохранённому исходному
разбору он вызывает метод платформенной таблицы +18; это не самостоятельный
UART write. Существующие AML-framing `117f7c` и UART-helper уже частично
восстановлены и требуют проверки привязки/повторного использования, а не
новой реализации транспорта с нуля. Сам d26ac в этом этапе не перенесён.

Контракт: стабильные валидные отдельные объекты, сериализованные завершающиеся
callbacks; флаги/индексы могут меняться на их границах. Вложенный cache-тест
использует выделенные таблицы на две цепи и три чипа; произвольная порча
указателей, гонки, реальные mutex/UART, ответы ASIC и повторный запуск процесса
не подтверждены. Никаких аппаратных команд, частот или напряжений не изменяется.

Старые исходники, production device_drv, `cgminer.c`, `Makefile.am`, эталон,
история upstream, пулы/devfee и лимит 32 слотов сохранены. Проблема владения
аргументами `65b3c` остаётся отдельной задачей перед живыми потоками.
