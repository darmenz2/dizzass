# B-01: отдельный безопасный UART write-all

Задача [#4](https://github.com/darmenz2/dizzass/issues/4), координация [#2](https://github.com/darmenz2/dizzass/issues/2).
База: `12446bed78a060a49364a80bcbfb4340b13f4f27` из `work/reconstruction`.

Это новый opt-in алгоритм последовательной записи байтов для будущей интеграции.
Он намеренно отличается от оригинального UART-helper. Модуль не подключён к
production, не выбирает порт, не открывает устройства, не формирует протокол,
не выполняет resync и не меняет `vn135_uart_write_legacy`.

## Что прочитано и переиспользовано

- `libbitmain/src/uart.c::vn135_uart_write_legacy` может до пяти раз повторить
  весь буфер и использует errno после короткой положительной записи. Его
  исследовательское поведение и тесты сохранены.
- `libbitmain/src/aml/chip.c::vn135_aml_send_command` создаёт кадр и удерживает
  внешнюю блокировку на время вызова helper. Автоматической замены helper нет.
- Последовательная ветвь `driver-bitmain.c::bitmain_write` уже продвигает
  указатель после положительного результата. Но она немедленно выходит при
  отрицательном результате, не ограничивает нулевой прогресс и не имеет общего
  deadline/точного счётчика в возвращаемом результате. Её контракт не подходит
  для прямого использования новым API. Код ядра/драйвера не изменён.
- Тестовая 11-байтная команда получается вызовами существующих
  `vn135_bm1398_set_config_packet` и `vn135_aml_frame_command`: девять байт
  SET_CONFIG и префикс `55 aa`. CRC, framing и кэш не переписаны. Использование
  encoder в тесте не устанавливает соответствие T21 и chip1398.

## API и владение

`dizzass_uart_write_all(io, data, length, deadline_ms, max_no_progress)` возвращает
структуру с `status`, `written` и `error`. `written` — сумма подтверждённых
положительных результатов write. Это не физическое завершение передачи и не ACK.

Три callback принимают один context:

| Callback | Результат |
|---|---|
| `write(context, suffix, remaining)` | `{count, error}`: count от 0 до remaining, либо ровно -1 и положительный errno |
| `clock(context, &now_ms)` | 0 и монотонное время в миллисекундах, либо положительный errno |
| `wait(context, deadline_ms)` | 0 — готовность, EINTR — прерывание ожидания, ETIMEDOUT/ECANCELED/другая ошибка — завершение |

Callback сам сохраняет системный errno до других вызовов. Адаптер не читает
глобальный errno; после `count >= 0` поле error игнорируется, включая старые
EAGAIN, EINTR и ECANCELED. Для ошибки count должен быть ровно -1; отрицательный
errno, count меньше -1 и count больше requested считаются нарушением контракта.

Вызывающий код обязан эксклюзивно владеть каналом **на протяжении всего кадра**,
включая ожидания. Блокировка отдельных попыток недостаточна. Здесь нет скрытых
mutex, файлового дескриптора или callback по умолчанию. Буфер остаётся неизменным,
context и callbacks — действительными до возврата. Вызовы из нескольких потоков
на одном канале требуют внешней сериализации.

## Порядок обработки

1. Нулевая длина возвращает успех без callbacks; NULL допустим. Для ненулевой
   длины обязательны data, три callback, положительный budget и длина не больше
   PTRDIFF_MAX. Реальную выделенную ёмкость указателя проверить невозможно.
2. Проверяется clock. Deadline уже абсолютный, в той же системе отсчёта;
   адаптер не прибавляет timeout и не может переполнить такое сложение.
3. Write получает только остаток. Положительный результат продвигает offset
   ровно на count; повторно принятый префикс не передаётся.
4. После EINTR проверяются время и бюджет, затем повторяется остаток. После
   EAGAIN/EWOULDBLOCK и нулевой записи выполняется readiness wait с тем же deadline.
5. Любая write-попытка без прогресса и каждый EINTR из wait расходуют одну
   единицу последовательного бюджета. Только положительная запись сбрасывает
   бюджет. Достижение лимита останавливает вызов до следующей попытки/ожидания.
   Поэтому даже неподвижные искусственные часы и бесконечные нули/EINTR не
   создают бесконечный цикл. Wait обязан действительно ожидать/уступать выполнение.

Clock проверяется перед первой записью, после положительной/нулевой/повторяемой
записи и после успешного/прерванного ожидания. `now >= deadline` означает timeout;
на checkpoint истечение времени имеет приоритет над исчерпанием бюджета.
Переход часов назад, в том числе числовое переполнение, даёт CLOCK_ERROR/EPROTO.

Если последняя запись приняла все байты, но последующий checkpoint обнаружил
deadline, результат — TIMEOUT с `written == length`. Эти байты уже приняты;
повторять кадр нельзя. Фатальная ошибка, ECANCELED или невозможный результат
callback возвращаются сразу, без дополнительного clock, сохраняя свою причину.

`error` содержит errno завершающего callback; для проверки входа генерируется
EINVAL/EOVERFLOW, для нарушенного callback — EPROTO, для deadline — ETIMEDOUT.
NO_PROGRESS содержит последнюю причину повторной попытки; у нулевой записи это
0, поскольку системная ошибка не сообщалась. При успехе error равен 0.
Ошибка/cancel/timeout всегда сохраняют подтверждённый progress. После невозможного
count адаптер сообщает только ранее подтверждённые байты: реальные побочные
эффекты некорректного callback установить нельзя.

Отмена кооперативная: ECANCELED может сообщить любой callback. Это не остановка
потока ОС. Write/clock/wait должны быть nonblocking либо ограниченными по времени.
Deadline не позволяет этому коду прервать зависший блокирующий callback.

## Проверки

`test_uart_safe.c` проверяет точную последовательность write/clock/wait, указатели,
смещения, оставшиеся размеры, принятые байты, статус, errno и число вызовов.
После каждой принятой порции накопленные байты должны совпадать с исходным
префиксом; входной буфер и защитные байты остаются неизменными.

Набор включает все 1 024 разбиения 11 байт в четырёх режимах: положительные
порции со старым errno; добавленный EINTR; добавленные EAGAIN/EWOULDBLOCK и wait;
нулевая запись и прерванный wait. Отдельно проверяются ошибки до/после прогресса,
отмена из всех callbacks, неизменный общий deadline при чередовании ошибок,
нулевой прогресс, переполнения размеров/времени, обратные часы, границы callback
и пустой ввод. Итого первоначального набора: 4 158 сценариев.

`test_uart_safe_negative.py` сначала требует успешный baseline, затем отдельно
компилирует восемь искажений: повтор префикса, ложный успех после короткой/нулевой
записи, влияние старого errno, потеря progress при ошибке, сдвиг deadline,
отказ от wait после нуля и сброс бюджета после ready. Принимается только
завершение с кодом 1 и `UART_SAFE_ASSERT`; ошибка сборки, сигнал и timeout не PASS.

Из корня checkout, отдельно для `CC=gcc` и `CC=clang`:

```sh
make -f integration/uart-safe.mk CC=gcc UART_SAFE_DIR=build/uart-safe-gcc uart-safe-test uart-safe-negative
make -f integration/uart-safe.mk CC=gcc SANITIZE=1 UART_SAFE_DIR=build/uart-safe-gcc-san uart-safe-test
make -f integration/transport-dispatch-135.mk CC=gcc TRANSPORT135_DIR=build/uart-safe-legacy-gcc dizzass-dispatch135-original dizzass-dispatch135-test dizzass-dispatch135-negative
cp build/uart-safe-legacy-gcc/libtransport.so build/libvn135_recovered.so
python3 tests/test_stage5_uart_differential.py
python3 tests/test_stage5_aml_uart_differential.py
clang --analyze -I. -std=c11 -Wall -Wextra -Wpedantic -Werror -Xanalyzer -analyzer-output=text integration/native/uart_safe.c
```

Новые GCC/Clang сборки и санитайзеры используют разные каталоги. Старые Python
наборы ожидают фиксированный путь `build/libvn135_recovered.so`, поэтому локальные
регрессии разных компиляторов выполняются последовательно. В CI они выполняются
на отдельных runners. Проверки оригинала и нового поведения намеренно раздельны.

Локальный Clang 14 PIE/ASan один раз завершил основной тест с SIGSEGV без отчёта
об ошибке памяти; тот же бинарник затем прошёл. Отдельная программа с пустым
`main` воспроизвела SIGSEGV в 6 из 12 запусков PIE/ASan в этом WSL, тогда как
12 запусков с `-fno-pie -no-pie` завершились с кодом 0. Поэтому именно host-harness
с SANITIZE=1 собирается non-PIE, сохраняя ASan, UBSan и проверку утечек. Это не
изменение production-флагов и не отключение санитайзеров. Логи первого сбоя
сохранены отдельно от окончательного результата; полный диагноз runtime/kernel
не заявляется.

Workflow `uart-safe.yml`: `pull_request` в `work/reconstruction` и ручной запуск,
точный head SHA, `contents: read`, без production/deployment и сохранённых
credentials. Логи и JSON отрицательных контролей доступны как CI artifacts.
Наличие workflow не подтверждает его исполнение: результат смотреть по SHA.

## Границы результата

Проверяются конечные детерминированные сценарии и память host-программы.
Не проверены физический UART/ASIC, реальные poll/write/clock, межпоточная
сериализация, аппаратный ACK, RX, восстановление соединения, слоты и запуск T21.
Предположения о времени жизни callback и эксклюзивном канале должен выполнить
будущий reviewed binding. Восстановление `b8e54` и владение аргументами потоков
`65b3c/65fcc` сюда не входят.
