# 0xd26ac — диспетчер транспорта и связка AML/UART

База: `8f7518a544d63ed4c6043b321b43d475a04c79a4`, дерево
`d7f5faf101bfcea6a0a599e5dcbe60937525f316`. Предыдущая запись регистра
`e4a74` уже опубликована; старые патчи повторно не применяются.

## Что восстановлено, что переиспользовано

`vn135_transport_send_135` воспроизводит обычное тело `d26ac..d2750`:
прочитать метод глобальной таблицы по смещению `+18`, вызвать его один раз
с неизменёнными device/payload/32-битной длиной и вернуть исходный статус.
Это не UART write, не поиск устройства и не преобразование результата в 0/-1.
Нулевые указатели/длина передаются методу, а не отклоняются диспетчером.
Непрозрачные условия с младшим битом `n*(n-1)` не создают дополнительных
вызовов: для любого 32-битного слова произведение соседних чисел чётно.
Исходные инструкции этих условий всё равно исполняются в oracle.

Проектный файл `libbitmain/src/transport-dispatch.c` — новая отдельная единица
офлайн-сборки. Имя исходного vendor-файла по одному этому телу не утверждается.
Тип таблицы содержит единственный нужный метод и новый callback-context;
это не ABI-совместимая копия глобальной структуры.

Добавлен типизированный адаптер `vn135_aml_uart_send_135`, соединяющий
существующие `vn135_aml_send_command` и `vn135_uart_write_legacy`.
Алгоритмы framing, CRC, UART retries и кэша не переписаны. Все прежние исходники,
в том числе AML, UART, `base.c`, register-write и общий интерпретатор, неизменны.

Штатный `driver-bitmain.c::bitmain_write` просмотрен: его последовательный
вариант продвигает указатель на уже переданные байты, в отличие от выбранного
legacy UART-helper. Поэтому это не эквивалентная замена исследуемой цепочки;
производственный драйвер не изменён.

## Привязка метода

Два PC-relative пути диспетчера ведут к GOT `5df454`, содержащему адрес
глобальной таблицы `68bf68`. Сама таблица, а не указатель из device, содержит
метод по адресу `68bf80` (`+18`).

Исполнен ограниченный исходный участок `d21dc`, заканчивающийся сразу после
установки метода, перед `d22dc`. Проверены 15 сочетаний платформы/подтипа.
Параметр platform=2 устанавливает **`117f7c`**, прежний AML send, при всех трёх
проверенных подтипах. Другие платформы НЕ принудительно направляются в AML:

| platform | subtype=0 | subtype!=0 |
|---|---|---|
| 0 | `10fa38` | `10f938` |
| 1 | `11d0cc` | `11d0cc` |
| 2 | `117f7c` | `117f7c` |
| 3 | `f8048` | `f8048` |
| 4 | `109740` | `109740` |

Это проверка установки метода, не полная инициализация, не физическое
определение контрольной платы T21. Селектор платформы и селектор чипа различны.
Автоматического выбора платформы новой C-функцией не добавлено.

## Явная связь представлений

Оригинал передаёт тот же адрес device в AML и далее в UART-helper. Ранее
восстановленные C-представления device/index и UART раздельны. Новый binding
явно связывает идентичность device с существующим `vn135_uart` и двумя
таблицами операций. Приведение одного несовместимого struct к другому запрещено.

Ошибки такого нового binding возвращают **-2 как защиту нового API**, а не
объявляются исходной семантикой `d26ac`. NULL source-device сохраняет исходный
путь AML с -1 до обращений к framing/UART. Остальные предусловия старых
AML/UART API, включая ограничение длины и обязательные callbacks, сохраняются.
`framing->write` не используется: адаптер намеренно вызывает старый UART-helper.

Внешняя блокировка AML и внутренняя блокировка UART — разные объекты.
Новая связка не объединяет их и сохраняет оба callback-context. Во время вызова
binding/таблицы операций стабильны; fd может меняться на границах callbacks.
Frame — временная память: указатель запрещено сохранять для отложенной отправки.

## Проверенное поведение транспорта

AML добавляет префикс `55 aa`, выделяет отдельный буфер, сериализует отправку,
вызывает UART-helper и затем всегда освобождает буфер после возвращения helper.
Девятибайтный payload SET_CONFIG превращается в 11 байт на границе OS-write.
Внешняя блокировка удерживается на всём протяжении внутреннего цикла повторов.

UART-helper выполняет не больше пяти попыток **всего буфера**, с ожиданием 20
после неполного результата при errno=11, включая ожидание после последней
неудачной попытки. Короткая положительная запись со старым errno=11 может
повторить уже переданный префикс. EINTR сам по себе не включает повтор.
Это исследуемое legacy-поведение, НЕ безопасная функция write-all.

Ровно сообщённое число байт определяет транспортный успех, не ACK ASIC.
Проверка/обновление кэша по-прежнему происходит после успешного транспорта.
Изменение индекса устройства/чипа или отключение кэша во время отправки
наблюдается родителем после её завершения; ошибки после передачи не откатываются.

## Проверки

Новый oracle использует существующий ARM32Difficulty без новых opcode.
Сравниваются исходные инструкции и скомпилированный C с конечными сценариями:

- **936 сценариев, 2 340 событий** для одного диспетчера: неизменённые длины
  вплоть до `0xffffffff`, нулевые указатели, произвольные знаковые статусы,
  смена метода между вызовами и повторный вход. Payload на этом уровне не читается.
- **15 проверок установки платформенного метода** исходным участком `d21dc`.
- **79 сценариев, 1 044 события** для исходной цепочки
  `d26ac -> 117f7c -> 10e6c0` против трёх соответствующих C-слоёв.
- **201 сценарий, 2 874 события** для исходных `e4a74 -> d26ac -> AML -> UART`
  вместе с исходными CRC и `107648/107ed0`, против C-композиции с прежним кэшем.
  Диспетчер, AML, UART и cache не подменяются успешными возвратами.
- Всего сравнений поведения: **1 216 сценариев / 6 258 событий**. В двух
  составных группах исполнено 374 532 шага оригинала; этот счётчик не включает
  прямую проверку диспетчера и отдельную проверку установки метода.
- Нативные тесты: **2 248 сценариев / 47 788 проверок**, включая защитные
  границы буфера, два уровня блокировок, сохранение скопированного payload,
  повторный вход, отказ выделения и защитные проверки нового binding.
- **7 отдельно собранных семантических мутаций** должны отвергаться именно
  несовпадением с оригиналом. Ошибка сборки, таймаут или случайное падение не PASS.

Реальные OS-write, malloc/free, mutex, errno, sleep и memcpy оригинала заменены
явными тестовыми эффектами. Внутренняя диагностика прежних AML/UART/cache API
исключена из сравниваемого trace и подсчитана отдельно; сообщение e4a74
сравнивается. Полное равенство всех логов runtime не заявляется.

GCC/Clang используют отдельные каталоги, native-набор повторяется с ASan/UBSan.
Дополнительно запускаются прежние register/PLL и historical AML/UART проверки.
Результаты команд фиксируются в логах, CI следует проверять по SHA коммита.

```sh
make -f integration/transport-dispatch-135.mk CC=gcc dizzass-dispatch135-original dizzass-dispatch135-test dizzass-dispatch135-negative
make -f integration/transport-dispatch-135.mk CC=gcc SANITIZE=1 dizzass-dispatch135-test
make -f integration/transport-dispatch-135.mk CC=clang TRANSPORT135_DIR=build/dispatch-clang dizzass-dispatch135-original dizzass-dispatch135-test dizzass-dispatch135-negative
```

## Граница и продолжение

Это завершает выбранную офлайн-цепочку до границы системной записи, но не
включает live OS-адаптер, ответы ASIC, RX, физическую плату, GPIO/power sequencing,
гонки потоков, обработку зависаний и аппаратную приёмку. Другие платформенные
методы не восстановлены этим адаптером. `device_drv` не подключался.

Следующий оставшийся метод цепной установки частоты — **`e34cc` (pulse width)**.
Отдельными условиями production остаются безопасная обработка коротких записей
и владение аргументами `65b3c`; legacy-поведение не исправлялось молча.
Пулы, devfee, реальные частоты/напряжения, лимит 32 слотов, cgminer.c и
Makefile.am не изменены; никаких команд аппаратам не отправлялось.
