# A-01: 0xb8e54 — сброс четырёх групп таблиц по цепям

Задача #3, координация #2. База `12446bed78a060a49364a80bcbfb4340b13f4f27`,
дерево `2e73cb80b2ccbb15d24d9a7deb3c51f65bcd23ac`.
Результат предназначен для PR из `chatgpt/b8e54-recovery` в
`work/reconstruction`, не для прямого push в общую ветку или аппаратного запуска.

## Назначение и происхождение

Тело `b8e54..b9094` очищает содержимое четырёх групп таблиц под глобальной
блокировкой. Это не остановка потока, не освобождение таблиц и не UART-команда.
Указатель глобальной таблицы `68be68` берётся через GOT `5df6ac`;
mutex имеет адрес `612aa0`. Эти же объекты использует аллокатор `b86fc`.
Его диагностика ссылается на `/tmp/build/src/backend/throttling.c`.

Связь установлена по PC-relative ссылкам, размерам выделения и девяти
ограниченным запускам успешных путей исходного аллокатора. В самой `b8e54`
нет строки с именем исходного файла: принадлежность к блоку throttling
подтверждается общими данными, а не прямой диагностикой этого тела.
Назначение каждого элемента таблиц не выдумывается; полная реализация
throttling или его инициализации этим этапом не заявляется.

Новая единица офлайн-сборки — `src/backend/throttling-reset.c`, функция
`vn135_throttling_reset_135`. Это новое проектное имя файла.
Прежний pending-модуль `src/backend/throttling.c` и весь `base.c` неизменны.
Нативная `cgminer.c::zero_stats` просмотрена: она сбрасывает статистику
майнера/пулов и вызывает driver callbacks, а не эти четыре таблицы.
Поэтому её нельзя использовать как эквивалент `b8e54`.

Переиспользовано существующее поле `general_model.expected_chips_48`.
Добавлены только ещё не представленные счётчики model+50/+60, проекции
четырёх групп и интерфейс count/platform/lock/unlock/zero. Эти структуры
не являются vendor ABI, приведения сырого backend к ним нет. Ассоциация
дополнительной model-view с существующей general-model остаётся стабильной.
Нового майнера, копии статистики cgminer, управления питанием или транспорта нет.

## Точное поведение

Сначала один раз вызывается `fe668` (количество цепей), затем читается
backend+18 (модель), затем `fdfbc` (платформа). На платформах, отличных от
**4 и 7**, функция возвращается без блокировки и очистки. Таким образом,
ранее выбранный AML-селектор 2 сам по себе не включает эту очистку.
Это не установление физического типа контрольной платы.

На 4/7 вызывается `5a6108` с глобальным mutex. Даже при количестве 0 или
отрицательном значении lock и unlock выполняются; строки не обрабатываются.
Коды ошибок lock/unlock оригинал не использует для новых развилок.
Восстановленное API возвращает void, как и игнорирующий результат caller
`663cc`; нулевой или ненулевой r0 исходного возврата не считается статусом
остановки оборудования.

Для каждого индекса от 0 до сохранённого количества минус один:

| Группа глобальной таблицы | Размер обнуления строки |
|---|---|
| +0 | `(uint32_t)model[0x60] << 3` |
| +4 | `(uint32_t)model[0x48] << 3` |
| +8 | `(uint32_t)model[0x50] << 3` |
| +c | `(uint32_t)model[0x48]` |

При NULL массива либо NULL конкретной строки только эта группа пропускается.
Непустой указатель при нулевом размере всё равно передаётся в `memset`.
Указатели массивов/строк и соответствующие размеры перечитываются перед
каждой операцией; перестановка обхода по группам вместо обхода по цепям
не объявляется эквивалентной. Исходный порядок групп — 0, 4, 8, c.

Модель захватывается **после count и до platform/lock**. Если последующий
callback изменил backend+18, текущий вызов продолжает использовать ранее
выбранную модель; изменения её полей при этом видны следующим операциям.
Количество цепей повторно не запрашивается. Беззнаковые сдвиги сохраняют
32-битный результат, а не расширяются неявно до host size_t.

Пятая таблица +10, указатели, размеры и backend-поля самим телом не очищаются.
После обхода выполняется ровно один unlock. Нет free, нового лога,
проверки активности каждой цепи, отмены потока, отправки команды или отката.
Непрозрачные условия `n*(n-1)&1` исполняются в oracle; их младший бит равен
нулю и при 32-битном усечении, поэтому дополнительные повторные ветви в C
не нужны. Это арифметическое свойство, не обход аппаратной защиты.

## Проверки

Сравнение неизменённых ARM-инструкций с C проверяет порядок/аргументы
вызовов, оба модельных объекта, указатели всех таблиц/строк, полные байтовые
буферы, защитные поля, backend и сохранённые регистры/стек оригинала.
В исходном ELF ничего не патчится. Общий ARM-интерпретатор не изменён.

- Прямой набор: **1 017 сценариев, 6 479 событий**.
- Вложенный набор: **64 сценария, 782 события**. Исполняется исходная
  `663cc -> b8e54`, а на стороне C используется старая остановка майнинга
  и новое тело. Остальные нижние операции `663cc` остаются заданными эффектами.
- Две группы: **102 758 шагов**, 172 посещённых адреса инструкций.
- Отдельно **9 проверок успешных путей аллокатора**: общий table/mutex,
  пять первоначальных выделений, четыре размера на каждую цепь. Отказные
  пути аллокатора не приняты и сам аллокатор в C не переносится.
- Нативный набор: **5 145 сценариев, 5 024 540 проверок**. Большинство
  проверок — побайтовые инварианты и регулярные переборы NULL-масок,
  не независимые аппаратные состояния. Здесь memset работает по реальным
  выделенным host-буферам; остальные операции инъецируются.
- **10 семантических мутаций** обязаны собраться и отвергаться именно
  расхождением с исходными инструкциями. Ошибка сборки/таймаут не считаются
  обнаружением. Проверяются платформы, момент захвата модели, размеры,
  нулевой count/length, игнорирование lock-ошибки и обязательный unlock.

Цели запускаются на GCC/Clang в разных каталогах, native-набор повторяется
с ASan/UBSan; прежние mining-stop/exit-cleanup — отдельные регрессии.
Команды и реальные результаты записаны в логе этапа/PR. Удалённый CI
проверяется по head/merge SHA PR, не выводится из наличия workflow.

```sh
make -f integration/throttling-reset-135.mk CC=gcc dizzass-throttle135-original dizzass-throttle135-test dizzass-throttle135-negative
make -f integration/throttling-reset-135.mk CC=gcc SANITIZE=1 dizzass-throttle135-test
make -f integration/throttling-reset-135.mk CC=clang THROTTLE135_DIR=build/throttle-clang dizzass-throttle135-original dizzass-throttle135-test dizzass-throttle135-negative
```

## Границы и следующий шаг

Требуются валидные стабильные объекты, массивы под всё захваченное положительное
количество, достаточный размер каждой достигнутой строки и завершающиеся
последовательные callbacks. Произвольные повреждённые указатели, слишком
короткие буферы, конкурентные изменения, реальные mutex и зависания не приняты.
Отсутствие дополнительной проверки размеров и продолжение после ошибки lock —
восстановленное поведение, не обещание безопасности для live runtime.

Новый модуль не связан с production device_drv. Нет изменения cgminer.c,
Makefile.am, прежних evidence/исходников, лимита 32 слотов, частот, напряжений,
пулов или devfee. Область UART safe-write задачи Codex #4 не редактировалась.

После независимого ревью и решения владельца о merge можно продолжить
оставшийся `fe218` внутри `663cc` (его платформенный метод ещё нужно установить),
либо согласовать следующий участок в #2. Реальные потоки/железо и безопасное
владение аргументами `65b3c` остаются отдельными задачами.
