# A-05 — светодиодные выходы `f98b8 / f9840` в остановке

Задача #18; координация #2. Независимая база:
`12446bed78a060a49364a80bcbfb4340b13f4f27`, дерево
`2e73cb80b2ccbb15d24d9a7deb3c51f65bcd23ac`.
Не включает неопубликованный A-04 и ожидающие ревью PR других этапов.

## Что перенесено

`vn135_led_clear_135` воспроизводит наблюдаемые вызовы и состояние `f98b8`;
`vn135_led_set_135` — соседней `f9840`. Это управление двумя выходами LED,
не отключение питания ASIC и не завершение потока.

Привязка к модулю `libbitmain/src/led.c` устанавливается через `f96a0`:
инициализатор содержит декодируемую строку исходного пути, получает два номера
через `fe558/fe5e0`, записывает слова `654aa8/654aac` и байт готовности `654ab0`.
Те же ячейки читают обе новые функции. Двенадцать ограниченных успешных
исполнений инициализатора проверяют эту связь. Сам инициализатор здесь не
перенесён, пути его отказов и физическое определение пинов не приняты.
Назначение цветов и активная электрическая полярность не выводятся из номеров.

Новый `libbitmain/src/led-output.c` — проектная единица офлайн-сборки.
Старый `led.c` со статусом pending сохранён как исторический материал;
не утверждается, что теперь реализован весь модуль LED.

## Точные различия

| Условие | `f98b8`, clear | `f9840`, set |
|---|---|---|
| Готовность | любой ненулевой байт | ровно `1` |
| Значение нижнему GPIO | `0` | `1` |
| selector 0 | первый пин | первый пин |
| selector 1 | второй пин | второй пин |
| selector 2 | первый, затем второй | первый, затем второй |
| Любой другой selector | без вызовов | без вызовов |

Селектор — полное 32-битное слово, а не младший байт. Например, `256`
не превращается в `0`. При ненулевой готовности `2` clear действует, но set — нет.
Это воспроизведение исходного поведения, а не рекомендация таких состояний.

Байт готовности проверяется один раз. После первого вызова selector=2 второй
пин читается заново, даже если callback изменил его или обнулил готовность.
Возврат GPIO игнорируется: ошибка первого вызова не отменяет второй. Новых
повторов, общей блокировки пары, задержек, rollback и диагностики LED нет.
Функции сами не записывают в свои глобальные ячейки и не завершают процесс.

Непрозрачная арифметика исходной f98b8 исполняется в oracle без патчей.
Произведение соседних 32-битных целых имеет нулевой младший бит; недостижимые
ветви не превращены в дополнительные вызовы. Сопоставляются наблюдаемые
вызовы/поля, не машинное время, caller-saved регистры и incidental return.
Вызывающие процедуры остановки не используют результат этих функций;
типизированные реализации имеют тип `void`.

## Повторное использование

`vn135_led_gpio_set_135` вызывает существующую `vn135_gpio_set_value_135`
(`124ba4`), не реализует второй GPIO-драйвер. Старая функция сохраняет свои
lock/path/fopen/fprintf/fclose/unlock и обработку отказа открытия. Для пинов
проверены знаковые пути, в том числе `0xffffffff -> gpio-1/value`; это контракт
исходного форматирования, не допустимый номер реального вывода.

Вложенный ARM-набор исполняет `f98b8/f9840 -> 124ba4` до системных эффектов.
Нативная сторона использует тот же ранее восстановленный GPIO-модуль.
Системные операции — детерминированные callbacks. Файл `/sys` не открывается.
Ошибки lock/print/close старого helper не получают новых выходов; ошибка open
даёт существующую диагностику GPIO. Успех helper не равен свечению LED или ACK.

`vn135_led_shutdown_step_135` — небольшой НОВЫЙ маршрутизатор для старого
shutdown step-интерфейса. Он отличает UNHANDLED, HANDLED и INVALID_BINDING.
HANDLED означает только распознавание шага, не аппаратный успех. Неизвестный
адрес не вызывает fallback; невалидная привязка не выполняет запись.

Существующие родители вызываются без изменений:

- `5f0fc` доходит до `f98b8(2)`: два запроса значения 0;
- `5fc54` доходит до `f98b8(1)`, затем `f9840(0)`: второй пин получает 0,
  первый 1 при готовности ровно 1. На готовности 2 происходит только первый
  из этих двух этапов;
- ранние выходы родителей не получают дополнительных LED-вызовов.

В родительском ARM-наборе исполняются настоящие исходные тела родителей и LED;
сам `124ba4` на этом уровне задан callback. Его тело сравнивается отдельным
вложенным GPIO-набором выше. Полной единой ARM-цепочки всех подсистем нет.
Прочие эффекты родителей остаются явными тестовыми границами, не устройствами.

## Выполненные проверки

- Прямые ARM/C сравнения: **2 166 сценариев, 1 192 события**. Все 256 значений
  готовности, селекторы 0..3 и граничные 32-битные слова, ошибки нижнего вызова,
  изменения пинов и готовности на границах вызовов.
- LED с исходным GPIO helper: **122 сценария, 980 событий**. Точные пути,
  формат/значение, обработка отказа открытия, порядок, повторное чтение пина.
- Исходные родители/политика остановки с LED: **63 сценария**, **2 296 событий
  родителя и 56 LED-вызовов**. Проверяются и пропущенные через ранние выходы пути.
- Provenance инициализатора: **12 успешных путей**, отдельно от сравнений C.
- Нативные тесты: **4 615 сценариев, 19 526 проверок**, включая **512 связок
  с двумя родительскими процедурами**, повторный вход, защитные поля и новый
  routing-контракт. Подсчёт включает регулярный перебор, не физические испытания.
- **10 семантических отрицательных контролей**: каждый обязан скомпилироваться
  и получить MISMATCH с оригиналом. Ошибка сборки, crash и timeout не засчитываются.

GCC и Clang используют отдельные каталоги; новый нативный набор повторён
с ASan/UBSan. Прежние GPIO/power и exit-cleanup запускаются как отдельные
регрессии. Статический анализ новой единицы и неизменность старых зависимостей
проверяются отдельно. Точные команды и результаты сохраняются в логах.
Статус удалённого CI проверяется только после публикации конкретного коммита.

```sh
make -f integration/led-output-135.mk CC=gcc LED135_DIR=build/a05-gcc dizzass-led135-original dizzass-led135-test dizzass-led135-negative
make -f integration/led-output-135.mk CC=gcc SANITIZE=1 LED135_DIR=build/a05-gcc-san dizzass-led135-test
# Для Clang использовать CC=clang и отдельные LED135_DIR.
```

## Ограничения и продолжение

Стабильные валидные объекты, последовательные завершающиеся callbacks,
обязательный достигнутый set_value. Методы/контекст не меняются во время вызова;
поля готовности/пинов могут меняться на границах. Реальные гонки, зависшие
системные операции, синхронность двух GPIO-записей, физическая полярность,
LED blink-loop и аппаратная приёмка не доказаны.

Стандартный cgminer имеет identify_device, но это не реализация данных двух
глобальных LED-вызовов. Производственный device_drv не подключался; старые
исходники, общие типы, доказательства, reference ELF и интерпретатор не менялись.
Никаких команд ASIC, смены пинов, частот, напряжений, пулов/devfee и 32-slot policy.

Следующий отдельный вопрос очистки — конкретная функция за backend+19c и её
жизненный цикл до удаления callback. A-04 отвечает только за замену записи,
не за завершение ранее вызванного обработчика. B-02/B-03/B-04 Codex не дублируются.
