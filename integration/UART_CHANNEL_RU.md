# A-14 — владение TX-каналом и завершение передачи перед освобождением fd

Задача #52, координация #2. База `work/reconstruction`:
`12446bed78a060a49364a80bcbfb4340b13f4f27`, дерево
`2e73cb80b2ccbb15d24d9a7deb3c51f65bcd23ac`.

Это НОВОЕ opt-in поведение Linux/POSIX, не восстановление очередной функции
VNish. Старый UART, исходники Codex, производственное ядро, доказательства и
ограничение 32 аппаратных слотов не изменены. Нового device_drv здесь нет.

## Повторное использование

`uart_channel.c` вызывает неизменённую `dizzass_uart_posix_write_all` из
A-13 / PR #51 (`4de412bdc0f2e4230d6c0e84b633a97105b15d21`). Она использует
неизменённый B-01 / PR #5 (`2c8ed9672c711ad643c56d22b235d799cee28a09`).
Четыре C/header-файла закреплены commit/path/Git blob/SHA-256 в manifest и
подготавливаются только в игнорируемом `build/a14-deps`. Их PR не слиты и не
считаются принятыми этим этапом. Алгоритм write-all, poll, часы, framing и CRC
не продублированы. Для примитивов синхронизации используются настоящие pthread.
Просмотренные util.c/driver-файлы базы не подставлялись как готовый аналог
владения этим каналом; доказательство идентичности такого аналога не заявляется.

## Контракт и последовательность

`create(&channel, fd)` создаёт непрозрачный объект с mutex и condition variable
на CLOCK_MONOTONIC. Объект ЗАИМСТВУЕТ уже открытый fd. Создание не открывает,
не дублирует, не закрывает и не проверяет устройство. Проверку неблокирующего
TTY/OPOST выполняет A-13 перед фактической непустой передачей.

`send` допускает ровно один полный вызов A-13 одновременно. Пока владелец
отправляет пакет или ждёт poll, остальные отправители ждут condition variable.
Mutex не удерживается во время write/poll, но флаг active сохраняет эксклюзивное
владение. Очередь использует тот же абсолютный срок, который затем без изменения
получает A-13: ожидание очереди не даёт пакету новый срок. Фиксированный FIFO-
порядок и справедливость планировщика не обещаются.

`stop` под mutex навсегда закрывает допуск и будит ожидающих отправителей.
Они возвращают CANCELED/ECANCELED без обращения к fd. Текущий вызов A-13
НЕ прерывается: он заканчивает передачу либо возвращает свою ошибку/таймаут.
Stop ждёт его завершения до собственного абсолютного срока.

- `stop == 0`: активного TX нет, новый TX через этот объект невозможен.
- `stop == ETIMEDOUT`: допуск уже закрыт, но активный вызов ещё может использовать
  fd. Закрывать или перенастраивать fd по этому результату НЕЛЬЗЯ. Нужно снова
  дождаться успешного stop, не продлевая исходный срок активного send.
- Повторный stop на остановленном неактивном объекте возвращает 0 даже при сроке 0.

Это **мягкая остановка**, не немедленная аварийная отмена и не электрическое
отключение. Очень большой срок активного send означает потенциально долгое
завершение. Верхний драйвер должен задавать подходящие конечные сроки. Никакой
таймер не прерывает зависший kernel driver или вытесненный планировщиком поток.

## Ошибки и подтверждённые байты

Любой НЕ-OK результат реально вызванного A-13 навсегда останавливает канал.
Это сознательно консервативная новая политика: вслед за неполным или сомнительным
пакетом не отправляется новый пакет автоматически. Сохраняются точные поля
status/written/error, в том числе written==length при позднем TIMEOUT и нулевое
продвижение при ошибке допуска A-13. Нет автоматического повтора, очистки UART,
исправления framing или сброса оборудования.

Ошибки проверки аргументов/часов/ожидания ДО вызова A-13 возвращают written=0,
не заменяют последний результат передачи и сами по себе не объявляют, что
пакет передавался. Обычный таймаут в очереди не останавливает чужую передачу.
Пустой пакет на открытом объекте — no-op без изменения last; после stop даже
пустой пакет получает CANCELED. Это явное отличие от отдельно вызванного B-01.

`snapshot` под mutex возвращает stopped/active/waiting и последний завершённый
результат нижнего вызова. Это не непрерывная телеметрия байтов активного send.
Принятые write байты НЕ доказывают drain, получение или ASIC ACK.

## Время жизни, fd и отмена потока

Один gate защищает только обращения через этот gate. Все алиасы fd, сторонние
записи, RX-потоки и перенастройка должны быть согласованы внешним владельцем.
Нельзя создать два независимых gate для одного канала и считать их общей
блокировкой. После успешного stop владелец может освободить fd только с учётом
всех ВНЕШНИХ пользователей. Модуль сам никогда не вызывает close.

Освобождение объекта — отдельный этап: прекратить выдачу новых ссылок, дождаться
stop==0, затем завершить/join ВСЕХ вызывающих потоков (включая ожидающих, stop и
snapshot), только потом destroy. Stop==0 не доказывает исчезновения этих ссылок.
При конкурентном входе в destroy поведение не поддерживается. EBUSY не позволяет
удалить открытый/активный gate; неожиданные ошибки pthread_destroy допускают
лишь повтор destroy. Сам fd не закрывается даже при успешном destroy.

Отложенная pthread cancellation отключается на время работы с gate и активного
A-13, восстанавливается после записи результата, снятия active и unlock.
Ожидающий pthread_cancel может затем не дать вызывающему получить return value.
Snapshot сохраняет только ПОСЛЕДНЮЮ передачу канала, не квитанцию каждого
запроса: последующий send может её заменить. После отмены нельзя приписывать
last конкретному запросу без исключения других отправок. В тестах stop сначала
закрывает очередь. Не использовать pthread_cancel для повтора пакета или мгновенного
прерывания. Асинхронная отмена, сигнальные обработчики, fork во время работы,
повторный вход в тот же gate и повреждённые pthread-объекты не поддерживаются.

Нормативные опоры (прочитаны при разработке):
- POSIX condition wait, абсолютный срок, spurious wake и атрибут часов:
  https://pubs.opengroup.org/onlinepubs/9799919799/functions/pthread_cond_clockwait.html
- POSIX состояния отмены потока:
  https://pubs.opengroup.org/onlinepubs/9799919799/functions/V2_chap02.html
- Linux предупреждения о close при конкурентном I/O и повторном использовании fd:
  https://man7.org/linux/man-pages/man2/close.2.html

## Фактически выполненные локальные проверки

GCC 14.2 и Clang 17, каждый отдельно:

1. **35 управляющих сценариев**: реальные pthread mutex/condition/threads,
   но один полный нижний A-13 вызов контролируется тестом. Проверены точные
   аргументы, единственный владелец, очередь/таймаут, spurious wake, init/wait/clock
   ошибки, остановка, два stop-потока, fault latch, сохранение всех полей результата,
   отложенная отмена активного и ожидающего отправителя. Это НЕ системный UART.
2. **5 настоящих PTY-сценариев**: четыре конкурентных пакета по 262144 байта
   дают 1 MiB без перемешивания; мягкая остановка позволяет активному пакету
   524288 байт завершиться и отклоняет очередь; полный буфер приводит к таймауту
   с проверкой точного принятого префикса; повторное использование номера fd
   после quiescence не вызывает TX через старый gate; отмена активного потока
   не оставляет active; второй независимый канал продолжает работать.
   Write-обёртка только наблюдает реальную ОС, не задаёт результаты.
3. Обе группы прошли ASan/UBSan с проверкой утечек; защиты не отключались.
4. **14/14 намеренных ошибок** нового адаптера скомпилировались и завершились
   UART_CHANNEL_ASSERT/exit 1. Baseline проходит тот же управляющий набор.
   Ошибка сборки, сигнал, таймаут или произвольное исключение не засчитываются.
5. **10 проверок staging** прошли в Python и Python -O: изменения входа/выхода,
   отказ перезаписи, лишний include, symlink, недопустимый каталог, отсутствие
   подготовленных зависимостей. Подготовка не выполняет сетевых запросов.
6. Пять дополнительных повторов обеих групп на каждом компиляторе прошли.
   Это повторы тех же сценариев с другим планированием ОС, не новые независимые
   доказательства и не тест пропускной способности.
7. Дополнительно **GCC ThreadSanitizer** прошёл обе группы без отчёта о гонке.
   Clang TSan не запускался. Этот конечный прогон не доказывает все interleaving.
8. Неизменённые транспортные регрессии: 1216 сравнений с исходными инструкциями,
   15 проверок выбора платформы, 2248 нативных сценариев и 7 отрицательных
   контролей; UART 3248 и AML/UART 689 сравнений — прошли на обоих компиляторах.
9. Clang analyzer не выдал диагностики; 8 прежних тестов границы ядра прошли.
   Полная производственная сборка и устройство T21 этим не проверены.

Базовый исходный архив и опубликованные патчи воспроизвели точное дерево базы
до изменений. Прямой git clone в локальном контейнере не прошёл DNS; локальный
коммит-якорь архива не выдаётся за исторический commit базы. Runtime-зависимости
прочитаны через GitHub и совпали с закреплёнными Git blob SHA побайтно.


Новые CI задания проверяют proposed/synthetic-merge tree, не выполняют merge.
Удалённый результат проверяется отдельно от локальных логов. Независимое ревью
этого модуля и решение владельца о merge ещё необходимы. A-12, аппаратная привязка,
полная RX/TX-жизнь, реальное питание и первая принятая шара остаются отдельными
этапами. Команд ASIC/физическому UART, изменения частот/напряжений/пулов/devfee,
production linkage и повторной публикации A-04 не выполнялось.
