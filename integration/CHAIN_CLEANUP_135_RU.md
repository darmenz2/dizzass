# B-02: исходная очистка цепи 0x5a9fc

Задача [#8](https://github.com/darmenz2/dizzass/issues/8), координация [#2](https://github.com/darmenz2/dizzass/issues/2).
База `12446bed78a060a49364a80bcbfb4340b13f4f27`, ветка `codex/chain-cleanup-135`.
Владелец оставил за собой `0xfe218`; этот адрес и A-02 не изменяются.

## Происхождение и повторное использование

Перенесено тело `5a9fc..5ac44`; литералы заканчиваются перед `5ac80`.
Полный исходный путь `/tmp/build/src/backend/chain.c` проверен по ссылке в
диагностике и XOR-декодированным байтам. `chain-cleanup.c` — новое проектное
имя отдельной единицы сборки, не утверждение об имени файла производителя.
Эталонный ELF имеет SHA-256
`b2663b3aa753cc14ae9d3b11a14d3d93c74b605a3e433b02101c3c17c69d95e9`.
Ранее независимая проверка извлечения из пользовательского архива 1.3.5
установила побайтное совпадение с этим ELF.

Переиспользованы `vn135_general_chain`, `vn135_route_chain`, `vn135_route_chip`,
`vn135_general_monitor`, поля `expected_chips_48` и `query_fault_87`, существующий
`vn135_chain_stop_ops` и всё тело `vn135_chain_auxiliary_stop_135` (`545a0`).
Общие заголовки и прежние функции не правятся. Добавлены только представления
недостающих `chain+80` и четырёх байт `chain+6c..6f`.

Нельзя заменить этот вызов существующей `vn135_chain_stop_135` (`56d18`): та
вызывает индикатор, устанавливает состояние 3, пишет причину остановки и
изменяет другой набор полей. Здесь такого поведения нет. Новый алгоритм
безопасного UART из B-01 не используется: эта задача сохраняет оригинал.

## Исходный порядок

1. Передать текущий `chain+18` и единицу в `fde14`, затем вызвать `10ed2c(100)`.
   Результаты игнорируются; реальных аппаратных вызовов в модуле нет.
2. После задержки перечитать backend из `chain+1c`, его model+18 и флаг
   model+87. В oracle выполняются сами `5e524` и `a720c`, не фиктивный успех.
   При ненулевых флаге модели и `chain+24` вывести сообщение строки 1840,
   выполнить существующий `545a0`, при его ненулевом результате — строку 1843.
   Номер цепи для каждого сообщения читается заново с 32-битным `+1`.
3. Захватить mutex цепи; ошибка lock не создаёт нового раннего выхода.
4. Обнулить слово +80, слова +30/+34/+38/+28 и байт +25. Обнулить **48** байт
   +40..+6f. Существующие 44 байта statistics и отдельные четыре байта
   статистического хвоста вместе представляют этот исходный диапазон.
5. Сохранить состояния 3, 4, 5; остальные 32-битные значения заменить на 2.
6. Снова прочитать backend/model и сохранить этот указатель модели. Для
   индексов от 0 до model+48 очистить у чипа слово +08, байт +50, восемь байт
   +58/+5c и 44 байта +18..+43. Ноль и отрицательное количество не входят
   в цикл. `route_chain.chip_count` не подменяет количество модели.
7. Вернуть исходный результат последнего unlock без нормализации.

Сами указатели массивов не обнуляются; +8c, fault+3c, индекс чипа, температуры
датчиков, причина остановки и остальные поля сохраняются. Исходный `memset`
представлен обнулением полей C; арифметики над temperature нет, включая NaN.
Размер существующего восьмибайтного представления проверяется при компиляции.

## Контракт

`vn135_chain_cleanup_135(view, ops, context, reply_scratch)` — изолированная
исследовательская функция. Структуры — типизированные проекции, не vendor ABI;
не допускается накладывать их приведением указателя на бинарные структуры.
Действия reset/exchange/delay/lock/unlock задаёт binding; аппаратных реализаций
по умолчанию нет. Log необязателен согласно существующему интерфейсу.

Идентичность самой цепи стабильна. На границах синхронных callbacks допускаются
замены backend/model/chip-array на валидные объекты. Все достигнутые количества
вмещаются в массивы; объекты модели, проекции и чипов не перекрывают очищаемую
память. Нет асинхронных изменений или реальных потоков. Чтения и записи внутри
обнуления не заявлены атомарными. Для `545a0` вызывающий код предоставляет
инициализированные два байта scratch: ошибка обмена может оставить их прежними.
Возврат unlock не доказывает остановку оборудования, снятие питания или ACK.

## Проверки и команды

Oracle исполняет неизменённые инструкции `5a9fc`, `545a0`, `5e524`, `a720c`.
Нижние reset/exchange/memset/mutex/delay/log моделируются явно. Сравниваются
аргументы, порядок и количество вызовов, состояние на каждой границе, обе
модели, оба массива чипов, сырые восемь байт temperature и конечный код.
Отдельные guards проверяют неизменность остальных байтов и полей.

Первоначальный набор: **961 сценарий / 6 212 событий / 143 126 инструкций**,
включая все 256 значений present, крайние состояния, нулевые/отрицательные
количества, отказ/успех на разных попытках auxiliary, ошибки нижних вызовов,
повторный запуск и изменения на границах callback. Нативный набор:
**865 сценариев / 20 463 проверки**, с настоящими memsets хоста и canaries.

Десять отрицательных контролей требуют успешной сборки, затем именно
`MISMATCH` с оригиналом: пропуск +80 или хвоста статистики, неверное состояние,
неверное количество, ранний захват модели, пропуск задержки, неверный источник
флага, ранний выход при ошибке lock, потеря результата unlock. Сначала обязан
пройти baseline; сигнал, timeout и ошибка сборки не считаются обнаружением.

Из корня checkout, отдельно для `CC=gcc` и `CC=clang` и разных каталогов:

```sh
make -f integration/chain-cleanup-135.mk CC=gcc CLEANUP135_DIR=build/b02-gcc dizzass-cleanup135-original dizzass-cleanup135-test dizzass-cleanup135-negative
make -f integration/chain-cleanup-135.mk CC=gcc SANITIZE=1 CLEANUP135_DIR=build/b02-gcc-san dizzass-cleanup135-test
make -f integration/thermal-routes-135.mk CC=gcc ROUTES135_DIR=build/b02-routes-gcc dizzass-routes135-original dizzass-routes135-test
make -f integration/exit-cleanup-135.mk CC=gcc EXIT135_DIR=build/b02-exit-gcc dizzass-exit135-original dizzass-exit135-test
clang --analyze -I. -std=c11 -DVN135_CHAIN_CLEANUP_135 -Xanalyzer -analyzer-output=text src/backend/chain-cleanup.c
```

Sanitizer-harness использует `-fno-pie -no-pie`: ранее в этой WSL-среде Clang
PIE/ASan падал и на независимом пустом main. ASan, UBSan и проверка утечек
включены; production-флагов здесь нет. B-02 не заявляет нового диагноза runtime.
CI работает с точным head SHA, read-only permissions, публикует логи и JSON.
Статус конкретного запуска смотреть в задаче/PR; наличие workflow не есть PASS.

## Пределы

Не проверены реальные цепи, UART/ASIC, mutex/потоки, повреждённые размеры,
перекрывающиеся объекты, весь runtime либо T21. `5ac80`, `fe218`, безопасное
владение аргументами потоков и production binding сюда не входят. Регрессия
старого exit-cleanup выполняется без изменения его callbacks: новый полный
вложенный oracle `5f0fc -> 5a9fc` этим PR не заявляется.
