# BM1368: нижнее применение частоты — 0xe249c

База: `5c19f122855805a8beea5f720bfcfb38aa9068d4`, дерево
`d2fc35ae20f7c5d68d8ed350348f2dcc3d062b67`. Продолжение `57a10`.

## Перенос и повторное использование

`vn135_bm1368_set_frequency_135` воспроизводит обычное управляющее тело
`e249c..e27c0` из исходного `libbitmain/src/chip/chip1368.c`.
Новый файл `libbitmain/src/chip/chip1368-frequency.c` — отдельная единица
офлайн-сборки проекта, не восстановленное имя файла производителя.
Старые модули, производственная сборка и общий ARM-интерпретатор не изменены.

Расчёт делителей `ff288` уже восстановлен в `libbitmain/src/pll.c`.
Адаптер `vn135_bm1368_frequency_solve_135` вызывает именно существующий
`vn135_pll_search_legacy`; второй алгоритм поиска не создаётся.
Интерфейс позволяет явно подставить этот адаптер либо контролируемый solver
для проверки развилок. В составных проверках используется настоящий старый
C-поиск против исполнения неизменённых инструкций `ff288`.

56-байтная таблица `5eb6c0`: reference=25, VCO min=2000, max=3200,
порог режима=2400, максимальные делители ref=2, feedback=250, post=7,
начальная ошибка=2.5. Это параметры поиска, НЕ безопасные режимы частоты ASIC.
Поле `reserved_16` старого общего типа здесь читается как порог режима.
Байты совпадают с таблицей старого BM1398, но упаковка регистра отличается:
поэтому `vn135_bm1398_pll_parameter_word` не используется как эквивалент.
Штатный `driver-bitmain.c` также не заменяет этот контракт.

## Поведение оригинала

1. Вызвать solver с исходной дробной частотой и таблицей. При ненулевом
   результате — диагностика строки 966, возврат -1 без чтения результата
   solver и без записей регистра.
2. Проверить VCO результата: диапазон **2000..3200 включительно**.
   Это VCO, а не непосредственно запрошенная частота цепи. Вне диапазона —
   сообщение строки 972 и -1.
3. Собрать слово регистра по исходным 32-битным операциям:

```
(VCO < 2400 ? 0x40000000 : 0x50000000)
| ((feedback & 0xfff) << 16)
| ((reference & 0x3f) << 8)
| (((post1 - 1) & 7) << 4)
| ((post2 - 1) & 7)
```

В C сдвиги и вычитания выполняются беззнаково. Поля результата solver
остаются существующими int32; их битовое представление преобразуется явно.
Округления запрошенной частоты к 50 или 100 в этой функции нет.

4. Вызвать **дважды** `e4a74(device,1,NULL,8,word)` с одинаковым словом.
   Первая запись выполняется без проверки результата. Результат только второй
   записи определяет возврат: 0 при её успехе, иначе строка 972 и -1.
   Пример: первый вызов вернул ошибку, второй 0 — итог 0. Повтор всегда ровно
   два вызова, это не цикл повтора до успеха. Между записями нет новой задержки.
5. Сообщение строки 972 содержит PLL number 0 и первоначальную запрошенную
   частоту. Индекс устройства читается после нижних вызовов. Отката нет.

Непрозрачные условия `n*(n-1)&1` не порождают новых циклов: младший бит
произведения соседних целых нулевой и после беззнакового усечения до 32 бит.
Oracle при этом исполняет исходные инструкции этих условий.

## Представления и границы

Параметр device соответствует подструктуре **chain+2b8** родительской `57a10`.
Его поле index+18 не объявляется тем же полем, что parent chain+18.
В тестовом адаптере оба объекта различны; связь задаётся явно.
Новых production-привязок, аппаратных записей или потоков нет.

`e4a74` остаётся интерфейсом register-write. Уже существующий
`dizzass_bm1368_command_encode` переиспользуется в тестовом callback для
формирования пакета, а не для отправки. Его результат отдельно сравнивается
с исходными инструкциями `e4a74` до первого обращения к транспорту.
Это НЕ перенос полного тела `e4a74`: транспорт, cache и его ошибки пока
не раскрыты этим этапом. Сам возврат 0 не подтверждает ответ чипа.

В старом вычислительном API PLL опущена внутренняя диагностика строки 73.
Она исключена из сравниваемого trace нового вложенного теста и подсчитана
отдельно (12 срабатываний в текущем наборе). Диагностика самой `e249c`
сравнивается. Полное совпадение логов всего runtime не заявляется.

## Выполненные локальные проверки

- **375 сценариев / 1 374 события**: исходная `e249c` с заданными результатами
  solver. Проверены границы VCO, маски делителей, отказы обоих вызовов,
  неинициализированный output при отказе solver, изменение index и повторный вход.
- **296 сценариев / 722 события**: исполнение оригинальных `e249c -> ff288`
  против нового тела и уже восстановленного C-solver. Всего двух групп:
  **671 сценарий / 2 096 событий**, 233 454 шага интерпретатора.
- **270 сравнений пакетов**: существующий C-encoder против исходного пролога
  `e4a74`, включая оригинальный CRC, до транспорта. Никакой отправки нет.
- **1 318 нативных сценариев / 22 468 проверок**, включая **112 последовательных
  связок `65fcc -> 57a10 -> e249c -> legacy PLL`**. Проверены первый/второй
  отказы записи и последующая ошибка pulse width; цепное решение использует
  ранее восстановленную `60a2c`. Нижние OS/аппаратные эффекты заданы явно.
- **11 семантических мутаций** должны собраться и быть отвергнуты именно
  несовпадением с неизменённым oracle, не ошибкой компиляции или таймаутом.

Новые наборы собираются GCC/Clang и повторяются с ASan/UBSan. Прежние chain,
worker, fall и BM1368 control тесты выполняются отдельно. Полное вложенное
исполнение оригинального worker и всех аппаратных процедур не заявляется:
вложенный оригинал здесь ограничен `e249c/ff288`, остальное — C-композиция.
Результаты CI проверять по SHA коммита; наличие workflow не равно success.

```sh
make -f integration/bm1368-frequency-135.mk CC=gcc dizzass-pll1368-original dizzass-pll1368-test dizzass-pll1368-negative
make -f integration/bm1368-frequency-135.mk CC=gcc SANITIZE=1 dizzass-pll1368-test
make -f integration/bm1368-frequency-135.mk CC=clang PLL1368_DIR=build/pll-clang dizzass-pll1368-original dizzass-pll1368-test dizzass-pll1368-negative
make -f integration/bm1368-frequency-135.mk CC=clang SANITIZE=1 PLL1368_DIR=build/pll-clang-san dizzass-pll1368-test
```

Контракт сравнения: конечные requested 0..1e9, конечный VCO результата,
корректные стабильные объекты, неизменяемая таблица callbacks/limits,
последовательные завершающиеся callbacks и обычная binary64 арифметика.
NaN/Inf, нестандартный FPSCR, произвольная порча указателей и конкуренция
потоков вне этой проверки. Ограничения входа -2 старого solver не объявляются
оригинальными: их область исключена из сравнения.

## Продолжение

Следующий нижний узел — **`0xe4a74`**, полная операция записи конфигурационного
регистра, а не повторная разработка её уже проверенного encoder/CRC.
Метод pulse width `e34cc`, физическое соответствие таблицы плате T21 и
безопасное владение аргументами родителя `65b3c` остаются отдельными задачами.
Производственные `cgminer.c`, `Makefile.am`, пулы, devfee, ограничения слотов
и реальные частоты/напряжения не менялись.
