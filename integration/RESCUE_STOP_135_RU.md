# 1.3.5: остановка rescue-service — 0x287a4

База: `feb35d8fd38931ebfc92ac7a2bb0a112fb6afd27`, дерево
`57a8c7ead1efa388c579ea0087b525dc3e26f2ec`. Этап продолжает опубликованную
очистку `5f0fc`, не требует повторного применения старых патчей.

## Что именно делает функция

`0x287a4` — не ещё одна общая очистка майнера. Она останавливает один отдельный
глобальный поток. Установлена связь с **rescue-service@btm**:

- создатель `26f54` передаёт `26fe8` в `5a55cc` и адрес handle `68b118`;
- при ошибке создания он ссылается на `src/frontend/rescue.c` и сообщение
  `Failed to create rescue service thread`;
- worker `26fe8` устанавливает имя `rescue-service@btm` и флаг `68b108`;
- `287a4` через исходные GOT-ячейки читает именно эти flag и handle.

Поэтому файл новой реализации — `src/frontend/rescue.c`. Это связь через
создатель, worker и общие поля: само тело stop-функции строки с путём не содержит.
Полные XOR-строки проверены по байтам и длинам соответствующих циклов, а не
по обрезанным эвристическим записям раннего отчёта stage1.

**Тело работающего сервиса `26fe8` этим этапом не восстановлено.** Его сетевые
операции, назначение запросов и связь с другими подсистемами здесь не заявляются.

## Перенесённое поведение

При нулевом флаге функция возвращается без библиотечных вызовов, даже если
handle ненулевой. При любом ненулевом байте флаг обнуляется **до** вызова self.
Затем handle читается после self. Если это тот же поток, выполняется detach
с сохранённым значением self; иначе — cancel, **новое чтение handle**, join с
NULL result. Ошибки detach/cancel/join игнорируются. Handle не обнуляется.

Нет дополнительных блокировок, повторов, таймаутов, изменений состояния backend,
команд питания, маркера stopped и выхода процесса. Если синхронный callback
снова установил флаг, функция не обнуляет его в конце. Повторный вызов и
повторный вход из callback при уже сброшенном флаге проверяются отдельно.

Две служебные глобальные переменные участвуют в непрозрачных условиях
`(n * (n - 1)) & 1`. Для любого 32-битного n произведение соседних чисел чётно;
усечение до 32 бит младший бит не меняет. Поэтому ложные ветви не перенесены
как новые циклы. Oracle всё равно исполняет **неизменённые инструкции** оригинала,
в том числе эти проверки, с граничными и случайными значениями служебных слов.

## Повторное использование и подключение

Последовательность совпадает с уже проверенным `shutdown_thread_135`. Вместо
дублирования тела добавлен узкий офлайн-адаптер `vn135_shutdown_thread_stop_135`
в конце `src/backend/base.c`; он вызывает существующий static helper.
`vn135_rescue_service_stop_135` в новом frontend-модуле использует этот адаптер.
Весь прежний префикс `base.c` сохранён побайтно, включая реализацию helper.

Существующие `vn135_shutdown_thread` и четыре поля `vn135_shutdown_ops`
переиспользованы, но rescue-slot — **отдельный объект**, не один из десяти слотов
backend. Представление — только типизированная проекция: исходные globals
расположены раздельно, это не их ABI-совместимый C struct и не host pthread_t.

Вызов из `5f0fc` остаётся на прежнем интерфейсе `ops.step(287a4, 0)`.
Новый helper позволяет явно связать его с rescue-slot. Такая связь выполнена
в составных тестах; автоматической регистрации производственного драйвера или
новой остановки реальных потоков не добавлено. Старое описание `287a4` как
неперенесённой границы в EXIT_CLEANUP_135_RU.md относится к предыдущему этапу.

Проверены существующие альтернативы настоящего cgminer: `thr_info_cancel`
в `util.c` дополнительно обнуляет handle и уничтожает semaphore; `__kill_work`
в `cgminer.c` управляет несколькими подсистемами и таймаутами. Это не эквиваленты
данного тела. Они не заменяются и не копируются в новое ядро майнера.

## Проверки

Исходный ELF используется только как данные ограниченного ARM-интерпретатора.
Новые ARM-opcode реализации не добавлены. Предыдущие oracle и native-тесты
не изменялись. Новая составная проверка расширяет их через явные тестовые
обёртки без подмены глобальных объектов старых Python-модулей.

- Прямое сравнение: **1 145 сценариев, 3 922 внешних события**, включая все
  256 значений байта флага, граничные handle, ошибки, изменения полей в callback,
  повторные вызовы и воспроизводимые случайные случаи.
- Вложенное сравнение: **89 сценариев**, **3 501 событие backend и 146 событий
  rescue**. Исполняются исходная `287a4` внутри `5f0fc`, выбранные пути `5e92c`
  с `5cea8` и `6b778`, и контрольная ветвь `5fc54`, не вызывающая rescue-stop.
  Сравниваются старый trace целиком, новый trace с состоянием backend и итоговые
  поля. Вызов `287a4` не заменён успешным callback.
- Нативный C-набор: **569 сценариев, 11 258 проверок**, включая canary-границы,
  повторный вход, независимость rescue-slot от backend, ранние выходы и
  включение helper между завершением backend-потоков и обработкой цепей.
- Четыре отрицательных контроля: поздний сброс флага, раннее чтение handle,
  отсутствие повторного чтения после cancel, пропуск join при ошибке cancel.
  Каждый вариант должен собраться, затем быть отвергнут именно несовпадением
  с оригиналом; произвольный сбой и ошибка компиляции не засчитываются.

GCC и Clang используют отдельные каталоги. Native-набор повторяется с ASan/UBSan.
Результат запуска, версии компиляторов и регрессии фиксируются в локальном логе
и CI по конкретному SHA; наличие workflow само по себе не считается успехом.

```sh
make -f integration/rescue-stop-135.mk CC=gcc dizzass-rescue135-original dizzass-rescue135-test dizzass-rescue135-negative
make -f integration/rescue-stop-135.mk CC=gcc SANITIZE=1 dizzass-rescue135-test
make -f integration/rescue-stop-135.mk CC=clang RESCUE135_DIR=build/rescue-clang dizzass-rescue135-original dizzass-rescue135-test dizzass-rescue135-negative
make -f integration/rescue-stop-135.mk CC=clang SANITIZE=1 RESCUE135_DIR=build/rescue-clang-san dizzass-rescue135-test
```

## Границы и дальнейшая работа

Возврат не подтверждает уничтожение потока: detach не является join, а ошибки
операций могут быть проигнорированы. Реальная конкуренция, отмена потока внутри
libc, зависший join, supervisor и повторный запуск процесса не испытывались.
Все callback последовательны и завершаются; идентичность выделенной памяти
стабильна. Неизвестные операции не превращены в успешные production-заглушки.

Остались другие нижние узлы очистки: `a6080/663cc`, `58d08/5a9fc`, backend+`19c`,
`108b40`, `f98b8` и аппаратные эффекты PSU OFF. Следующим отдельным участком
можно разбирать `a6080`. Тело сервиса `26fe8` — самостоятельная, более широкая
задача, его нельзя считать готовым по восстановленной остановке.

`cgminer.c`, `Makefile.am`, `util.c`, прежние тела и эталон сохранены.
История upstream, лимит 32 слотов, пулы, devfee, частоты/напряжения не меняются.
Это офлайн-перенос функции, не прошивка для установки и не приёмка T21.
