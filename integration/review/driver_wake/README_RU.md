# R-14 — остановка паузы и пробуждение кооперативного scanwork

Issue #88. Основа — R13 c028671b8a0d532d02a7c563d31d1e348272bc22.
Это намеренное небольшое изменение настоящих cgminer.c/miner.h.
Нового майнера, рабочей очереди, цикла fill/scan или аппаратного драйвера нет.

## Поведение

`cgminer_request_queued_stop` сначала фиксирует прежний односторонний флаг
и будит getq под прежним stgd_lock. После снятия блокировки первый запрос
делает cgsem_post каждому опубликованному потоку этого cgpu. Семафор
сохраняет уведомление, даже если поток ещё находится перед sem_wait.
Повторные запросы не накапливают дополнительные токены.

Очередной hash_queued_work использует общий mt_disable с проверкой stop
перед ожиданием и после пробуждения. Пробуждение ради остановки не вызывает
thread_enable. Если обычный thread_enable сам запросил stop, update_work
больше не вызывается. У прежних неочередных mt_disable-пользователей сохранён
старый контракт ожидания/повторного включения.

Добавлен НЕОБЯЗАТЕЛЬНЫЙ `device_drv.queued_stop_wake(cgpu)`. Он вызывается
после установки флага, вне staged mutex, при каждом явном запросе, включая
повтор после ошибки. Callback обязан идемпотентно будить собственное ожидание
scanwork: проверка собственного условия и переход в ожидание должны быть
согласованы его блокировкой. Он не должен ждать завершения scanwork/потоков,
вызывать join, выполнять аппаратные команды или рекурсивно вызывать stop.
Короткое получение его mutex допустимо: жёсткого срока всего запроса нет.

Возвращается первая ошибка getq broadcast или driver wake. Ошибка не снимает
stop: драйверное пробуждение можно явно повторить. cgsem_post сохраняет
прежнюю аварийную политику ядра при ошибке семафора. NULL callback означает,
что произвольное ожидание scanwork по-прежнему должно завершаться средствами
этого драйвера: новое поле само по себе не прерывает неизвестные функции.
Уже допущенные enable/update/scan callbacks могут закончить работу при гонке;
никакого атомарного отзыва операции или синтетического количества хешей нет.

## Владение и совместимость

До запроса stop нужно завершить публикацию списка `cgpu->thr`. Каждый ненулевой
элемент — живой правильный thr с инициализированным sem. Указатель массива,
количество, драйвер, его данные и все потоки сохраняются до окончания запросов.
Нельзя одновременно выполнять hotplug-публикацию/удаление, повторную регистрацию
или конкурентные запросы stop. Не вызывать API из signal handler либо удерживая
stgd_lock/блокировку, которую захватит queued_stop_wake.

Обе существующие точки выделения массива thread pointers теперь используют
cgcalloc: пропуски после неудачного thread_prepare остаются NULL. Это не делает
частично опубликованный массив пригодным для конкурентного обхода.

Новый указатель в device_drv требует пересборки ядра и всех его пользователей.
Нулевые штатные инициализаторы не включают callback автоматически. Прежний
публичный get_work остаётся блокирующим. Начальный miner_thread семафор также
получает уведомление: уже начатый thread_init не отменяется, но очередной
hash_work видит stop, после чего выполняется прежний thread_shutdown.

Контроллер отдельно останавливает TX/RX/submit, затем соединяет ВСЕ нативные
потоки и исключает внешние ссылки, и только после этого освобождает объекты.
Данный API не делает join, аппаратное выключение/drain, новую epoch или повторное
использование32 слотов. Автоматического сброса stop/перезапуска нет. Пауза и stop
не заменяют полноценное расписание/учёт работы будущего производственного драйвера.

## Проверки

14 новых сценариев: пауза внутри настоящего hash_queued_work, граница перед
реальным sem_wait, stop до входа в паузу, нормальное возобновление, stop внутри
thread_enable, прежний mt_disable, три ожидающих потока с NULL-пропуском,
повторный stop без переполнения токенами, блокирующий scanwork тестового драйвера,
граница condition wait, отсутствие callback, ошибка wake и явный повтор,
изоляция другого cgpu и начальный miner_thread wait/shutdown.

Драйверный стенд использует настоящий pthread_cond_wait с собственной блокировкой,
а не подменяет hash_queued_work, miner_thread или get_work. Вызов wake проверяет,
что staged mutex свободен и stop уже опубликован. Контрольный scanwork возвращает
0 хешей, потому что ожидание само по себе не выполняет вычисление. Подготовка
пакета использует прежние A16/PTY и контрольные задания, не физический ASIC.

Прежние537 случаев и73 отрицательных контроля сохраняются. Новый набор добавляет
14/8, итого551 случаев и81 контроль. Ожидаются конкретные assertion/exit1, не
авария, ошибка компиляции или timeout. Адаптирован лишь поиск исторической записи
R13 в supersedes: её точное прежнее содержимое проверяется вместе с актуальными
байтами; старые C assertions не убраны. Для повторного использования fixture
в прежний тест R13 добавлен только main-embedding guard.

Запуск из чистой исходной ветки с установленными host-зависимостями:

```
python3 -B integration/review/driver_wake/test_runner.py
python3 -B -O integration/review/driver_wake/test_runner.py
python3 -B integration/review/driver_wake/run.py --cc gcc-14 --baseline icarus --out build/r14-gcc --mutants
python3 -B integration/review/driver_wake/run.py --cc clang-17 --baseline icarus --out build/r14-clang --mutants
python3 -B integration/review/driver_wake/run.py --cc gcc-14 --baseline icarus --out build/r14-san --sanitize
```

`--groups driver_wake` выбирает только14 новых сценариев. Runner требует
committed исходники и новый output, не скачивает данные/пакеты, не меняет refs.
Прямые test/core TUs и адаптеры проверяются санитайзерами; остальные библиотеки
не объявляются полностью инструментированными. Конкретные завершённые результаты
и ошибки публикуются отдельно, без выдачи focused прогонов за полный набор.
