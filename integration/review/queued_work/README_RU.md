# R-09 — передача задания из штатной очереди cgminer в управляемый TX

Задача #78. Основа: точный R-08 `611bbf10b7faffa2a87be8326653eced618e4d03`.
Это вызываемый helper для будущего `device_drv.queue_full`, не новый майнер,
не зарегистрированный драйвер и не разрешение аппаратного запуска.

`dizzass_queued_work_send` берёт одно задание через настоящий `get_queued`,
передаёт тот же указатель в существующий `io_send_work`/A-16 и затем вызывает
настоящий `work_completed`. Не создаёт другой очереди, копии работы вне
прежнего реестра, сетевого стека, планировщика или алгоритма SHA.

До получения задания проверяются аргументы, работающий lifecycle и абсолютный
срок TX. При таком отказе очередь и выходной отчёт не меняются. Сам get_queued
выполняет прежнюю проверку устаревания: NULL может означать как отсутствие
задания, так и его штатное освобождение со счётчиком discard.

После получения задания оригинал удаляется из core queued_work ровно один раз
при любом результате, включая отказ метаданных, ошибки подготовки/копирования,
гонку остановки и неопределённую отправку. Отчёт содержит исходный work_id,
наличие handoff/completion, отдельные ошибки метаданных, вызова lifecycle и
вложенный результат A-16. Return0 не означает отправленные байты или принятую
шару. При отказе оригинал не возвращается в очередь автоматически.

Копия в native_jobs (если подготовка завершилась) сохраняет жизнь задания для
раннего/позднего RX после освобождения оригинального core work. Освобождение
core queued_work не освобождает аппаратный слот. Слот назначает вызывающий
код; ограничение32 и запрет недоказанного переиспользования не меняются.
Текущая передача ограничена старым маршрутом platform2/algorithm0/variant2.

## Предусловия и владение

Необходимы настоящие инициализированные native очереди/qlock/scheduler locks,
корректные work/pool/job_id и живые pools. Нативная stale_work сама использует
эти объекты до дополнительной проверки метаданных. Helper не предназначен
для произвольных повреждённых указателей. Один последовательный владелец
очереди; никаких конкурирующих age_queued_work/work_completed над полученным
заданием. Прежний flush_queue для unqueued указателя остаётся под qlock.

Вызывающий код устанавливает совпадение thr/cgpu/io/jobs/submitter/порта. Здесь
нет автоматической проверки этой аппаратной связи или создания lifecycle.
Для строгого RX нужно передать lifecycle, созданный через create_crc5; helper
не переводит unchecked lifecycle в строгий. После pool update/flush/reset
нужны прежние внешние lifecycle-правила, не автоматическое продолжение.

Deferred cancellation исключена до удаления core work и публикации отчёта.
Отмена может быть доставлена при восстановлении состояния ИЛИ на следующей
точке отмены; нельзя требовать единственный момент доставки. Память отчёта
должна пережить отмену. Асинхронная отмена/reentry не поддерживается.

R-10 усиливает этот контракт: lifecycle отдельно считает active_queue до
work_completed и публикации receipt. При удержании этого окна stop возвращает
таймаут, а не quiescent. Однако это не подтверждение возврата вызывающей функции:
перед освобождением cgpu/pools/io/реестров всё равно необходимо исключить новые
внешние ссылки и соединить все вызывающие потоки. Стенд сохраняет это окно и
проверку отмены, теперь требуя таймаут и запрет преждевременного уничтожения.

## Проверки и воспроизведение

49 новых сценариев:13 preflight,6 пустых/stale,8 отказов метаданных,
11 ранних CRC-ответов с разными размерами чтения плюс отмена отправителя,
4 ошибки копирования, частичная/поздняя отправка, stop после get_queued,
отмена перед core completion, сохранность другого queued work и32 слота.
Используются реальные функции cgminer, qlock, PTY и Stratum-очередь.
Входное native work размещается стендом в unqueued_work, как после fill_queue;
сам get_work/пул-сеть не запускается. Нет заявления о полном driver loop.

Предыдущие390 сценариев/37 контролей не изменены. Новый runner расширяет R-08
до439 сценариев/44 скомпилированных смысловых контролей. Сигнал/таймаут/ошибка
компиляции не считается обнаружением ожидаемой ошибки. Санитайзеры проверяют
те же позитивные случаи после обязательной независимой pthread-cancel пробы.
Прямые test TUs/адаптеры инструментированы, остальные support-библиотеки нет.

```sh
python3 -B integration/review/queued_work/test_runner.py
python3 -B -O integration/review/queued_work/test_runner.py
python3 -B integration/review/queued_work/run.py --cc gcc-14 --baseline icarus --out build/r09-gcc --mutants
python3 -B integration/review/queued_work/run.py --cc clang-17 --baseline icarus --out build/r09-clang --mutants
python3 -B integration/review/queued_work/run.py --cc gcc-14 --baseline icarus --out build/r09-san --sanitize
```

Каталоги результата должны быть новыми. Runner архивирует текущий commit,
проверяет фактические файлы компиляции, не скачивает данные и не меняет refs.
--groups queued_work выполняет только49 новых случаев и прежние native guards.
Полные результаты и сохранённые ошибки подготовки — в комментарии PR/evidence.

Частоты, напряжения, защиты, devfee, аппаратные эпохи и32 слота не меняются.
Native device_drv регистрация, queue scheduling/scanwork, hardware discovery,
инициализация и доказанный аппаратный drain остаются незавершёнными задачами.
