# R-06 — единое проверяемое дерево R-02…R-05

Задача #72, координация #2. Это кандидат для ревью и объединения исходников,
не прошивка T21 и не разрешение на аппаратный запуск. Повторная проверка тем же
ассистентом не заменяет независимое ревью другим специалистом.

## Состав и история

Принятая база `f646f18f304e295134ffd37e007a62bfa1dbfa30` уже находится в истории
R-05 `e820932bd9618acf8fb5b008ef5a8abadd88d572`. В новом кандидате к нему
добавлено полное содержимое R-03 `66869a587e36acfd6e561f75215c1d4f07f071fa`,
включающее R-02. Оба настоящих удалённых коммита используются как родители
нового merge-коммита. Основные ветки и исходные PR не изменяются этим действием.

Полные исходные деревья восстановлены из предоставленных архивов и проверены
по Git tree SHA до объединения. Только три общих файла различались:
`integration/native_jobs.c`, `native_jobs.h`, `native_submit.h`.
Для них явно выбрана предложенная версия R-03. Все остальные общие файлы
побайтово совпали; новые файлы обеих сторон сохранены. `manifest.json`
содержит происхождение и хеши критических входов. Никакая часть принятой базы
не заменена старым снимком. Локальные Git-коммиты сборки — архивные якоря,
не поддельная история удалённого репозитория.

Два нужных тестовых файла R-01 перенесены побайтово из `cacbc87e` на их исходные
пути: `test_stack.c` и `evidence/cancel_probe.c`. Остальной draft R-01 не принят.
Производственные функции R-02…R-05, A-16, UART, парсер, work/pool, SHA и очередь
Stratum не переписаны. Новый C-файл — только тест, не очередной майнер.

## Проверка текущих файлов

Старые suite.mk используются с `*_DEPS=.`: реестр, inbox, RX-owner, lifecycle,
UART и A-16 компилируются из этого дерева. Каталоги `build/*-deps` вообще
не создаются. Старые тела тестов и проверки утверждений остаются неизменными.
Четыре workflow отдельных этапов на этой ветке направлены на общий runner с
выбором соответствующей группы; первоначальные ветки сохраняют свои workflow.
Это переход с исторических ограничений снимка на текущую композицию, а не
подавление результатов. Полный workflow отдельно запускает все группы вместе.

`compile_guard.py` выполняет настоящий GCC/Clang и сохраняет аргументы,
контрольные суммы C-файла и зависимостей, действительно выбранных компилятором.
C/headers из build-каталогов, внешних временных каталогов или с неожиданными
байтами отклоняются. Системные заголовки и точные сгенерированные configure
заголовки учитываются отдельно от отслеживаемых исходников. Обычная сборка
ядра дополнительно проходит существующую проверку списка production sources
и символов. Это свидетельство конкретной сборки, не проверка всех компиляторов.

## Наборы

- R-02: 25 сценариев сохранения/проверки ранних ответов.
- R-03: 39 сценариев реального native submit/Stratum queue.
- R-04: 38 сценариев владельца RX и остановки.
- R-05: 29 сценариев согласованной остановки целых операций.
- R-06: 66 новых сценариев: 64 запуска с четырьмя конкурирующими отправителями,
  влияние общей остановки submitter на другую цепь и точный ticket TX→RX→submit.

Итого 197 сценариев за полный прогон. Гонки имеют три расписания: остановка
до допуска, конкуренция с остановкой и завершение отправок до остановки.
Для конкурирующего случая не задаётся фиктивное число победителей: проверяется
баланс всех 256 попыток, сохранность отказных выходов, каждый реальный пакет
и отсутствие повторной отправки. До destroy все вызывающие потоки соединены,
даже когда уже получен quiescent. Число assertions зависит от планировщика.

24 прежних смысловых мутанта извлекаются из неизменённых описаний исходных
runner'ов и компилируются на общем дереве. R-02 изменяет первое вхождение в take;
R-03 использует исходное ограничение функции. Остальные сохраняют прежнюю
область замены. Успехом считается только ожидаемый assertion/exit 1, не падение,
таймаут или ошибка сборки. Новые проверки guard отдельно отклоняют подмену
источника, каталога include и выход за дерево.

Санитайзерный прогон сначала требует успеха независимого pthread-cancel
примера; затем выполняет те же 197 сценариев с ASan/UBSan и обнаружением утечек.
Прямые тестовые единицы и включённый cgminer.c инструментированы; прочие
вспомогательные объекты/библиотеки ядра собраны обычно. Старые проблемы GCC11/
Clang14 не объявляются исправленными; здесь явно выбраны GCC14/Clang17.
Нет заявления о TSan или доказательстве всех возможных чередований потоков.

## Воспроизведение

После получения этой ветки и установки обычных host-зависимостей:

```sh
python3 -B integration/review/combined_rx/run.py --cc gcc --baseline icarus --out build/r06-gcc --mutants
python3 -B integration/review/combined_rx/run.py --cc clang-17 --baseline icarus --out build/r06-clang --mutants
python3 -B integration/review/combined_rx/run.py --cc gcc --baseline icarus --out build/r06-gcc-san --sanitize
```

Укажите установленный GCC14; `--cc gcc-14` выбирает его явно. Без `--baseline`
используется ANTS2/no-libcurl для изолированного хоста без USB dev headers.
Драйвер ANTS2 не запускается. Только `cgminer --version` и offline-тесты.
`--groups early_rx,rx_submit` выбирает ограниченный прогон; его итог не равен
полному. Runner не скачивает файлы, не ставит пакеты и не меняет Git refs.
Архивируется текущий закоммиченный кандидат; изменённые входы и существующий
каталог результата отклоняются. Полные commands/exit/log hashes, head/tree и
compiler receipts находятся в указанном каталоге, включая неудачи.

## Границы вывода ревью

Основные контракты совместимы: captured ticket проверяется внутри допуска,
PENDING не публикуется преждевременно, native submit не повторяется по ложному
признаку принятия, остановка ждёт полных finish/notify операций. Вывод о каждом
конкретном запуске нужно брать из results.json и отчёта PR, не из этого описания.

Общий submitter действительно останавливает допуск других использующих его
цепей, не переводя автоматически их реестры в pause. Это документированная
граница одноканального контроллера; необходима координация всего устройства.
RX join/quiescent не означают исчезновение внешних ссылок, аппаратное отключение,
очистку старых ответов, новую epoch или разрешение повторно использовать слоты.

Парсер не проверяет CRC; поток поддерживает только подтверждённый вызывающим
кодом формат. Не реализованы полный аппаратный запуск, device_drv, voltage/
frequency/thermal protection интеграция или безопасный физический drain.
PTY-партнёр выдаёт известный nonce; попадание в настоящую очередь cgminer —
не подтверждение шары от ASIC или внешнего пула. Лимит 32 слотов сохранён.
