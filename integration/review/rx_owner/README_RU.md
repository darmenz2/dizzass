# R-04: один владелец приёма RX

Задача #66, PR #67. Новый opt-in Linux модуль, не производственная регистрация
`device_drv`. База: принятая после C-01 `f646f18f`, дерево
`f5e98d5047e3b3e10d5408d6236a736efb6c7b80`. Существующие исходники не изменены.

## Что реально связано

`rx_owner` запускает один pthread, который читает предоставленный TTY, сохраняет
состояние прежнего потокового парсера, передаёт nonce в прежний bounded inbox
и вызывает R-03 captured dispatch. Используются настоящие native work/copy/free,
submit_nonce, target/hash, дедупликация и очередь Stratum cgminer. Нет второго
майнера, собственного SHA, новой очереди заданий или повторной реализации UART.

Принятые UART/A-16, parser и native_nonce компилируются из текущего дерева.
Пять ещё НЕ принятых R-03 файлов из #64@66869a58 (native_jobs.c/.h,
native_submit.h, early_rx.c/.h) являются явными тестовыми зависимостями.
Они лежат только в новом каталоге build/r04-deps; старые tracked native_jobs не
заменяются. Ещё два файла #59@cacbc87e — вспомогательная PTY-обвязка и независимая
cancel-проба. Все семь проверяются по commit/path/Git blob/SHA256.
Этот PR не принимает и не объединяет R-02/R-03 автоматически.

## Жизненный цикл и контракты

Один управляющий поток последовательно вызывает create/start/join/destroy.
Только notify, request_stop и finished допускают параллельные обращения.
Перед destroy нужно исключить ВСЕ внешние ссылки, включая уведомляющие потоки.
Рабочий поток единолично владеет парсером и inbox. Никто другой не читает тот же
порт/его aliases; соответствие jobs, submitter и порта одной цепи задано снаружи.

create заимствует открытый читаемый O_NONBLOCK TTY с raw-настройками,
VMIN=1/VTIME=0. Проверяет, но не меняет flags/termios, не выбирает baud и не
открывает путь устройства. Файл, aliases, jobs, submitter, pool и callback context
живут до join. Единственный собственный дескриптор — nonblocking eventfd для
пробуждения. После TX finish/изменения реестра следует notify: ранние ответы
повторно обрабатываются без новых UART-байтов. Периодический poll тоже повторяет
проверку; poll_ms — настройка планирования хоста, НЕ барьер аппаратной свежести.

Один проход читает не больше256 байт и завершает не больше64 dispatch-событий.
Размер inbox остаётся1..1024 ответов, аппаратных work-слотов по-прежнему32.
PENDING сохраняется; частичная ошибка копирования приводит к повтору с ожиданием,
не к потере записи. Переполнение и остальные неустранимые ошибки завершают поток
с точным reason/detail. Шум учитывается согласно старому parser; REGISTER и
REGISTER_FILTERED явно передаются callback. CRC старым parser НЕ проверяется.
Ни разобранный регистр, ни QUEUED, ни local valid_nonce не означают ASIC ACK.

request_stop — только кооперативный запрос. Он будит poll, но не отменяет уже
допущенный native submit или выполняющийся callback. Его завершённый результат
передаётся callback до выхода. Рабочий поток держит deferred cancellation
выключенной; callback не должен включать её, блокироваться бесконечно или
повторно входить в inbox/submitter. Разрешены только notify/request_stop владельца.
Длинные/заблокированные native locks и callback не получают магического deadline:
join блокирующий, жёсткой границы времени здесь нет.

join защищает собственный учёт и копирование отчёта от отмены управляющего
потока; лишь после этого восстанавливается его прежний режим cancellation.
Отмена может помешать доставке возвращаемого кода, но не оставляет уже завершённый
join неучтённым. Повторный join возвращает тот же отчёт; finished не заменяет join.

Отчёт сохраняет количество оставшихся ответов, байтов незавершённого кадра и
необработанного хвоста прочитанного блока. При destroy эти значения/байты
освобождаются без новых submit. Перезапуска и автоматической смены epoch нет.
HUP/ERR обрабатываются fail-closed, даже при POLLIN: последний остаток kernel RX
не объявляется прочитанным или аппаратно очищенным.

Успешный join означает ТОЛЬКО завершение этого RX-потока. TX может продолжать
держать тот же fd! Нужны отдельный stop/join всех TX-пользователей и aliases,
согласование submission gate и физического оборудования. Никакого power-off,
доказанного drain, отзыва уже поставленных в очередь шар или разрешения заново
использовать аппаратный слот этот модуль не выдаёт.

## Проверки

Новый набор —38 сценариев:11 размеров ограниченных реальных read-запросов;
notify и периодический повтор без новых данных; actual A-16 early RX;
частичный кадр и хвост блока при stop; смешанные noise/nonce/register;
EINTR/EAGAIN/EIO/EOF и настоящий PTY hangup; overflow при ещё активном TX;
copy failure/retry; paused/old epoch/empty; callback error;
stop внутри настоящего submit;32 отправки и нормальная upstream-дедупликация;
filtered/special register; cancellation контроллера во время join;
повторное использование номера fd после RX join И TX release;
четыре параллельных notifier; pause раннего ответа без новых RX-байтов.

Реальные ядро/очередь/PTY/pthread не заменены успешными заглушками. Peer выдаёт
известный исторический nonce, а ошибки syscall и переход epoch явно внедряются
в отмеченных тестах. Это не ASIC-хешрейт, физический unplug или принятая пулом шара.
Ограничение read size изменяет запрос, а не придумывает возвращаемый syscall count.

Чистые локальные GCC14.2 и Clang17 сборки:38 сценариев и51 настоящий submit_nonce
в каждом нормальном/ASan+UBSan запуске. Число assertions включает ожидания и
зависит от планирования. Все7 скомпилированных смысловых мутантов обнаружены
на обоих компиляторах по ожидаемому R04_ASSERT/exit1, не по падению/таймауту.
Независимая pthread-cancel health-проба прошла до sanitizer-наборов.

Старые native-submit/jobs/nonce/hash и8 source-boundary проверок прошли с теми же
assertions. Для локальной ANTS2 конфигурации без libusb-dev test-only host_compat.h
добавляет лишь объявление opaque libusb_context. Clang analyzer новой реализации
завершился без диагностик; отдельная строгая компиляция C также прошла.
Runner:6 тестов в Python и6 в Python -O. TSan/полное доказательство всех interleavings
не заявлены. Под ASan/UBSan включены root core test TU и прямые модули; остальные
core objects/libraries обычной сборки, не весь cgminer инструментирован.

## Воспроизведение

После read-only получения точных dependency commits из manifest:
```
python3 integration/review/rx_owner/test_runner.py
python3 -O integration/review/rx_owner/test_runner.py
python3 integration/review/rx_owner/run.py --cc gcc --out build/r04-gcc --mutants
python3 integration/review/rx_owner/run.py --cc clang --out build/r04-clang --mutants
python3 integration/review/rx_owner/run.py --cc gcc --out build/r04-san --sanitize
```
`--baseline icarus` требует dev-пакеты хоста; локальные проверки использовали
неизменённый ANTS2/no-libcurl core, без запуска драйвера. Runner архивирует текущий
закоммиченный кандидат, проверяет исходники и семь dependency blobs, отказывается
перезаписывать каталог, сохраняет команды, exit codes и хеши полных логов.
`--deps-from` позволяет проверить те же байты офлайн, не утверждая наличие
исходной Git-истории в архивной копии. Runner не выполняет fetch/install/ref writes.

Локальные команды/хеши — results.json и приложенный архив доказательств.
CI отдельно проверяет exact PR head на GCC14/Clang17 Ubuntu24.04/Icarus; его итог
не выводится из самого наличия workflow или успешного source-snapshot job.
Работа выполнена в изолированной среде чата, не MainPC. Заблокированные действия
на MainPC не повторялись. Нет production registration, настоящего pool sender,
настроек напряжения/частоты/защит/devfee или изменений shared refs.
