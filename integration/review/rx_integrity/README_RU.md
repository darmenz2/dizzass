# R-08: CRC5 на управляемом RX-пути

Issue #76. Основа — непринятый R-07/#75, `000237f56f9112db10117dd4dade6029c1d44899`.
Это дополнительная интеграция существующего CRC5-helper, не второй майнер,
не восстановленная проверка из RX-потока VNish и не разрешение на установку.

## Разрыв, который закрывает изменение

`integration/rx_crc5.c` уже проверял полный девятибайтовый payload в старом
`native_tx_channel`. Поток `rx_owner` R-04 до этого использовал только
исторический parser и CRC не проверял. Новый код повторно использует тот же
`dizzass_bm1368_reply_crc5` и прежний `vn135_crc5_bits`; их байты не изменены.

Добавлены `dizzass_rx_owner_create_crc5` и `dizzass_io_create_crc5`. Они создают
**те же** owner и lifecycle с неизменяемым строгим режимом. Поддерживается
только прежний контракт CRC-helper: raw chip selector 4, variant 2, payload 9
байт, special_mode 0. Неподдерживаемые профили отвергаются, скрытого перехода
на режим без проверки нет. Сам selector не доказывает модель физического ASIC.
Конфигурация порта и обнаружение оборудования остаются внешними обязанностями.

Старые `create` сохраняют явно **непроверяющий CRC** режим для совместимости с
предыдущими контрактами и тестами. Это не исправление всех RX-путей по умолчанию.
Производственный caller, которому нужна эта гарантия, должен использовать
строгие конструкторы; производственный driver этим PR не регистрируется.
Структуры событий и отчётов расширены: потребуется пересборка callers,
совместимость с ранее скомпилированными двоичными структурами не заявляется.

## Обработка кадра

После существующего framing проверяются все 72 бита payload, включая бит вида
ответа и CRC. При несовпадении выдаётся `DIZZASS_RX_INTEGRITY_REJECTED` с точным
статусом и **недоверенным** raw-message для диагностики. Нет постановки в inbox,
копирования work, хеширования/submit и учёта native share/HW-error. Callback может
запросить остановку или вернуть ошибку. Иначе следующий кадр обрабатывается.

Для проверенных register, queued/rejected и dispatched-событий устанавливается
`integrity_verified`; для legacy-режима и повреждённых кадров он false. Отчёт
содержит `crc5_required`, `crc_checked` и `crc_rejected`. Счётчик относится к
полным кадрам, а не к шуму или повторным попыткам dispatch. Deferred-ответ после
проверки CRC по-прежнему привязан к первоначальным epoch/serial/chain/slot.

Правильная CRC — не аутентификация, не принадлежность заданию, не ACK, не
свежесть эпохи и не доказательство nonce. Исторический parser не изменён: при
вставке/потере байтов его способ поиска границы остаётся прежним. Новый режим
не объявляется корректирующим ошибки кодом и не обещает ловить все многобитные
искажения. Таймауты, cancellation, borrowed resources и 32 слота не изменены.

## Проверка

Новый набор: 167 сценариев. Из них 144 — каждый одиночный бит в nonce и register
payload, в отдельном PTY/owner-контексте. Проверяется отсутствие native submit,
копирования и статистики; специальный бит вида ответа тоже входит в набор.
Далее 11 размеров чтения раннего корректного ответа, 90 конфигураций в одном
сценарии допуска профиля, обычный/filtered register, повреждённые и корректные
кадры в одном блоке, настоящий lifecycle -> RX -> Stratum queue -> stop,
пустое задание, повтор после partial-copy, callback stop/error, неполный кадр,
legacy-совместимость и все 32 слота. Одинаковый исторический nonce в 32 слотах
намеренно даёт 1 valid + 31 native duplicate, а не измерение производительности.

`generate_vectors.py` использует независимое полиномиальное деление Python
для 34 фиксированных **синтетических** кадров. Это не аппаратные захваты и не
исполнение reference ELF. Существующие CRC-файлы зафиксированы по хешам.
Шесть новых смысловых мутантов дополняют прежние 31. Полный набор содержит
390 сценариев (223 прежних + 167 новых), 37 отрицательных контролей.
Фактические результаты запуска публикуются в описании PR и архиве доказательств:
существование сценария не означает его успешного выполнения.

Прежние C-проверки не изменены. В четыре тестовых Makefile добавлена только
линковка существующего rx_crc5.c. Manifest общей сборки явно пересмотрен для
шести изменившихся зафиксированных входов, с сохранением прежних хешей в
`supersedes` и `input_revisions.json`. Другие зафиксированные входы неизменны.
Компилятор по-прежнему проверяет реальные tracked-файлы, не build/*-deps копии.
ASan/UBSan инструментируют прямые тестовые единицы и адаптеры, не все библиотеки
поддержки. Обязательная независимая pthread-cancel probe сохраняется. TSan и
доказательство всех возможных чередований не заявляются.

## Воспроизведение

После checkout одного точного кандидата и установки host build dependencies:

```sh
python3 -B integration/review/rx_integrity/test_runner.py
python3 -B -O integration/review/rx_integrity/test_runner.py
python3 -B integration/review/rx_integrity/run.py --cc gcc-14 --baseline icarus --out build/r08-gcc --mutants
python3 -B integration/review/rx_integrity/run.py --cc clang-17 --baseline icarus --out build/r08-clang --mutants
python3 -B integration/review/rx_integrity/run.py --cc gcc-14 --baseline icarus --out build/r08-gcc-san --sanitize
```

Без `--baseline icarus` используется ANTS2/no-libcurl host-конфигурация для
среды без libusb-dev. Её driver не запускается: только `--version` и offline
тест. Runner не скачивает зависимости, не меняет refs и не запускает аппаратный
майнер. Каталоги вывода должны быть новыми. `--groups rx_integrity` — только
167 новых сценариев и шесть новых контролей, не полная регрессия.

Работа выполнена в изолированной среде чата; MainPC не использовался.
Стек остаётся кандидатом для ревью, без слияния и без разрешения аппаратного
запуска. Дальше нужны приёмка API и отдельные аппаратные configuration/drain/
epoch/device_drv-проверки, а не вывод о готовности прошивки из CRC или PTY.
