# R-03: отложенный RX → штатный native submit

Задача #63, PR #64. Явная зависимость от **необъединённого** R-02/#62
`fe768caf`; принятие этой зависимости и объединение C-01 остаются отдельными.
Новый модуль не создаёт второй майнер, очередь work/pool, SHA или сетевой стек.

## Изменение

`dizzass_submitter_run_captured` проверяет исходный ticket (epoch/serial/chain/slot)
внутри той же блокировки реестра, где проверяются состояние задания и его
параметры и создаётся нативная копия для submit. Это не последовательность
`ticket_live` → обычный `run` с окном повторной привязки по номеру слота.
Старый `dizzass_submitter_run` сохраняет сигнатуру и поведение через общий
внутренний путь. Проверка и копирование используют настоящее cgminer work.

`dizzass_early_rx_dispatch` использует **существующий** inbox R-02 и возвращает
один завершённый результат за вызов. PENDING сохраняется; более поздний готовый
ответ может пройти первым. Терминальные отказы задания являются явными событиями
без обращения к ядру. Ошибка допуска, включая частичную ошибку strdup, оставляет
запись и выходной объект неизменными. STOPPED/WRONG_THREAD/UNSUPPORTED_WORK нельзя
скрывать бесконечным повтором: это повод для обработки ошибки вызывающим кодом.

После состоявшегося native-вызова запись удаляется ровно один раз — даже если
ядро отклонило nonce, обнаружило дубликат, отбросило stale или не добавило share
в замороженную очередь. Повтор по `native_valid_nonce == false` недопустим.
Статус 0 и `native_called` означают только обращение к штатному `submit_nonce`.
`meets_target` не означает постановку в очередь или принятие пулом.

Отдельной предварительной проверки хеша через `take` здесь нет: диспетчер сразу
идёт через проверенный допуск к настоящему submit, сохраняя штатный путь ядра.
Обычный `take` остаётся доступным для инспекции без отправки; удаление записи
использует один общий внутренний helper. Эти два способа не обрабатывают одну
и ту же запись повторно.

## Границы владения и свежести

Это вызываемый шаг **одного последовательно работающего владельца RX**, а не
новый поток чтения UART и не регистрация device_drv. Все операции inbox, включая
обработку callback-ов, должны быть невложенными и сериализованными. Один общий
submitter на cgpu обслуживает все его цепи; обходить его прямым submit нельзя.
Владелец исключает deferred cancellation на всём участке dispatch и обработки
receipt. Тест с отменой подтверждает эту последовательность, но не добавляет
автоматическую защиту для произвольного вызывающего кода. Async cancellation
и рекурсивный вход в inbox/gate не поддерживаются.

Проверяется актуальность **при допуске и копировании**. Пауза после этого не
отзывает уже выданную копию. Реестр разблокирован перед native-вызовом, поэтому
hw_error может безопасно поставить его на паузу. Для прекращения последующих
допусков управляющий поток сначала останавливает submitter. Даже успешный stop
не удаляет уже добавленные cgminer shares и не отключает ASIC.

Ограничено число просмотренных записей, а не время выполнения: gate/core могут
блокироваться. Нет аппаратного барьера старых ответов, автоматической смены epoch,
новой dedup-политики или изменения 32 слотов. Пул и связанные native-объекты должны
пережить все вызовы и обработку очереди.

## Выполненные локальные проверки

Изолированная среда чата, **не MainPC**. Исходный архив получен через read-only
GitHub Actions; его полное дерево сверено с `c99e3daca20fc27246596c2b0ce010747af77572`.
Все 12 зависимых файлов A-16/UART/R-01 проверены по Git blob и SHA-256.
Локальная Git-история является архивным якорем, не восстановленной историей GitHub.

GCC 14.2 и Clang 17 отдельно собрали обычное ядро ANTS2 без libcurl и исполнили
только `--version` и хостовый harness; драйверы и сеть не запускались.
**39 сценариев, 887 проверок нового набора** на каждом компиляторе, плюс отдельные
проверки PTY-helper. Все шесть скомпилированных смысловых мутантов обнаружены
нужными R03_ASSERT/exit1. Ошибка сборки, сигнал или зависание не считаются успехом.

Реальная A-16 пишет через PTY. Контрольный peer отправляет ответ 11 размерами
фрагментов до окончания send. Новый dispatch сохраняет PENDING, затем вызывает
реальный submit_nonce; сохранённая копия проходит native-хеширование и оказывается
в настоящей `pool.stratum_q`, откуда её забирает только тест. Исходный work к тому
моменту изменён и освобождён после sender join. Пул ничего не принимал.

Дополнительно проверены: старый serial после NOT_SENT/reprepare; старый epoch;
pause/retire/quarantine; четыре частичных отказа копирования; остановленный gate;
ошибка привязки потока; неподдерживаемый work; pending перед готовым ответом;
переполнение/stop inbox; native stale-политика (включая оба варианта submit_stale),
submit_old, target и duplicate; callback pause после допуска; отмена RX-владельца;
32 реальные A-16 отправки и 32 диспетчеризации. Один и тот же известный nonce в
последнем тесте даёт один valid и 31 native-дубликат — это не статистика ASIC.

Оба независимых sanitizer-health примера здесь прошли, затем все 39 сценариев
прошли ASan/UBSan с leak detection на обоих компиляторах. Инструментированы root
cgminer.c, включённый в test TU, и прямые адаптеры; прочие core objects/libraries
обычные. Test-only non-PIE флаги унаследованы от R-02. Старые GCC11/Clang14 health
ошибки из R-01/R-02 остаются ошибками, эти результаты не «исправляют» их.

Старые R-02 (25 сценариев), native-submit/jobs/nonce/hash и восемь source-boundary
тестов пройдены. Clang analyzer запускается отдельно; его фактический журнал
сохранён. Новый runner имеет три теста в Python и три в Python -O.

Сохранены две начальные неудачи: неверно заданная stale-политика теста и
оптимизированный из таблицы символов test_nonce. Исправлены только fixture/link
flags; ни один runtime-отказ не замаскирован. Детали, хеши и exit codes — в
`results.json` и полном архиве журналов. CI на Icarus проверяется отдельно.

## Воспроизведение

После read-only fetch коммитов из manifest R-02:

```sh
python3 integration/review/rx_submit/test_runner.py
python3 -O integration/review/rx_submit/test_runner.py
python3 integration/review/rx_submit/run.py --cc gcc --out build/r03-gcc --mutants
python3 integration/review/rx_submit/run.py --cc clang --out build/r03-clang --mutants
python3 integration/review/rx_submit/run.py --cc gcc --out build/r03-san --sanitize
```

`--baseline icarus` требует обычные libusb/libcurl development dependencies.
`--deps-from /путь/к/проверенным/blobs` — отдельный offline-режим, проверяющий те же
хеши без утверждения о наличии исходных Git-коммитов. Runner требует закоммиченные
входные файлы и создаёт новый каталог; не меняет refs, не устанавливает пакеты и
не обращается к сети. Ошибка health останавливает sanitizer-run до приложения.

Требуется независимое ревью дополнительных API и принятие общей версии R-02/R-03.
Производственный RX-reader, аппаратная инициализация, stop/drain и первая
аппаратная/принятая пулом шара не выполнены этим этапом.
