# B-07: запуск рабочих потоков `0xc3b54`

Задача [#28](https://github.com/darmenz2/dizzass/issues/28), координация
[#2](https://github.com/darmenz2/dizzass/issues/2). Независимая база
`12446bed78a060a49364a80bcbfb4340b13f4f27`, ветка `codex/work-start-135`.
Только десять новых файлов; production-сборка и старые интерфейсы не изменены.

## Исходное поведение

`vn135_work_start_135` восстанавливает весь `c3b54..c3db3`, включая возврат.
Операции ОС и logger остаются обязательными внешними callbacks. Адреса рабочих
функций передаются как числовые identities, не вызываются как host pointers.
Модуль позволяет сравнивать последовательность с оригиналом до подключения
проверенного native driver; сам потоков не запускает.

Исходная последовательность:

1. `5a50e8` инициализирует scratch атрибута, `5a50f8` получает значение `1`.
2. `5a60dc(633af0, NULL)`, `5a4a08(633b08, &attribute)`.
3. `5a60dc(633ba8, NULL)`, `5a4a08(633bc0, &attribute)`.
4. `5a50e0(&attribute)` завершает использование атрибута для инициализации.
5. Последовательно вызывается `5a55cc` для трёх рабочих процедур:

| Поле backend | Процедура | Как получен адрес |
|---|---|---|
| `+1060` | RX `c4054` | PC-relative literal |
| `+1068` | producer, исходно `c2498` | **live** чтение slot `5df978` после успешного RX create |
| `+1058` | TX `c4b18` | PC-relative literal |

У каждого create второй аргумент `0`, четвёртый — тот же backend. Это не
передача scratch атрибута в create. Проверяется только результат create:
ноль продолжает последовательность, любой ненулевой int32 завершает её
через сообщения и возврат `-1`. Только три нулевых результата дают `0`.
Ошибки всех семи операций инициализации/атрибута игнорируются оригиналом.

`fa0c4` получает шесть исходных аргументов. Первые три — identities
`5e9659,5e962e,5e9660`, пятый — `1`; строки сообщений не заменяются догадками.

| Отказ | Четвёртый аргумент (line) | Шестой аргумент (message identity) |
|---|---|---|
| RX | `31d` | `5e96d3` |
| producer | `308`, затем `322` | `5e9758`, затем `5e96fd` |
| TX | `291`, затем `327` | `5e971d` в обоих вызовах |

Внутри исходной функции нет отмены/join уже созданных потоков, destroy объектов
синхронизации при отказе или обнуления handles. Callback может записать handle
даже при ненулевом результате — эта запись сохраняется. Добавление rollback
изменило бы исходное поведение, поэтому здесь его нет. Это также означает,
что функция сама не доказывает безопасное завершение частично запущенной системы.

## Контракт и повторное использование

View содержит отдельные ссылки на три uint32 handles, backend identity и
live producer-entry slot. Это проекции для сравнения, **не** vendor backend
layout и не native `pthread_t`. Существующие `work/pool`, SHA, Stratum,
очереди, RX/TX bodies и ядро cgminer не дублируются. Зависимостей от ожидающих
review PR #17/#22/#26 нет; их функции не импортированы и не исполняются здесь.

В `util.c` рассмотрен `thr_info_create`: он сначала вызывает `cgsem_init`,
затем один `pthread_create`. Дополнительный semaphore и отсутствие всей
координации делают его неэквивалентной заменой `c3b54`. В production продолжают
использоваться нативные типы и механизмы cgminer; данный модуль туда не включён.

Все callbacks и объекты обязательны, действительны, отдельны и существуют
весь вызов. View identities и ops неизменны. Значения handles и producer-entry
могут меняться на сериализованных callback-границах; нет модели асинхронных гонок.
Callbacks получают scratch только на время вызова, не сохраняют указатель после
возврата. Значения `value` для attribute init/destroy нормализованы к `0`:
в оригинале значим только указатель; у `5a50f8` дополнительно значимо `1`.

Оригинальный prologue: push32, frame pointer=entry_sp-8, sub sp16;
четырёхбайтовый scratch находится в `entry_sp-36` и до первого callback не
инициализируется. API явно принимает `attribute_initial` — произвольные
исходные биты scratch. Поэтому тесты отказа init не подменяют их нулём или
успешной инициализацией. Host C-код использует определённое начальное значение,
а не вызывает undefined behavior чтением неинициализированной C-переменной.

## Доказательства

Архив пользователя: `vnishnet-t21-aml-nand-v1.3.5.tar.gz`, SHA-256
`20fabdd66255889315e61ae2a33ff2e4623566ca430f1cb8c90d9b938dc7b43c`.
Повторное извлечение дало 6 228 004 байта `usr/bin/cgminer`, SHA-256
`b2663b3aa753cc14ae9d3b11a14d3d93c74b605a3e433b02101c3c17c69d95e9`.
Процесс vendor ELF не запускался.

Фактически выполнена Ghidra 12.1.4, ARM:LE:32:v8, JDK 25.0.4.1.
Полные script/C/asm/headless log включены в evidence JSON; шесть диапазонов
ELF и 25 адресных ссылок проверяются checker. Типы декомпилятора предварительны;
порядок аргументов и обращения к памяти сверены с A32. IDA Free для ARM не применялась.

Python oracle исполняет **оригинальные инструкции всего `c3b54`** от prologue
до возврата. Общий ARM-интерпретатор не изменён, новых opcodes не добавлено.
Перехватываются только внешние init/attribute/create/logger. Сравниваются
аргументы и состояния на каждой границе, результат, все 0x1348 байт backend,
scratch, handles, producer slot и моделируемые записи init в четыре объекта.
Защитные байты и неизменность view проверяются отдельно. Присутствующие в
Ghidra parity-ветви не патчатся: x*(x-1) имеет чётный младший бит при любых
32-битных значениях, в том числе с переполнением.

## Выполненные локальные проверки

GCC 11.4 / Clang 14, для каждого:

- 863 original comparisons, 8 605 callback events, 60 255 ARM steps,
  134 наблюдавшихся instruction addresses; расхождений нет. Число PC не
  является доказательством всех возможных внешних состояний.
- Native и ASan/UBSan: 4 608 сценариев / 802 656 проверок. У sanitizer binaries
  test-only `-fno-pie -no-pie` из-за ранее воспроизведённого WSL PIE startup сбоя.
- 18 mutants собраны и отклонены по семантическому расхождению с 863 fixtures
  оригинала; baseline прошёл. Ошибка сборки, crash или timeout не считаются
  успешным обнаружением. Проверяется, в частности, преждевременное чтение
  producer entry, потеря handle после ошибки и количество/аргументы логов.
- Старые route/TX88: 7 names, 16 caller snapshots, 10 selections, 2 worker sets;
  128 packets, 36 CRC comparisons; sanitized bounds — 11 225 проверок.
- Старый backend resume: 1 335 original scenarios / 50 406 events;
  native 332 scenarios / 27 279 assertions.
- Старый backend prepare: 1 742 original scenarios / 36 222 events;
  native 2 634 scenarios / 185 657 assertions.

Clang analyzer завершился без диагностик. Санитайзеры в этом наборе относятся
к новому startup и старым route bounds; backend resume/prepare выше проверены
как обычные native/original регрессии, без повторного sanitizer build.

Воспроизведение:

```sh
make -f integration/work-start-135.mk CC=gcc START_DIR=build/b07-gcc all sanitize negative regressions backend-regressions
make -f integration/work-start-135.mk CC=clang START_DIR=build/b07-clang all sanitize negative regressions backend-regressions
```

CI проверяет точный head PR и сохраняет логи, JSON старых регрессий и каждый
mutant log. Его фактический результат публикуется в issue/PR после завершения.
Работа реальных pthreads, bodies RX/producer/TX вместе, native device_drv,
полная прошивка, ASIC и принятые пулом шары этой проверкой не подтверждены.
