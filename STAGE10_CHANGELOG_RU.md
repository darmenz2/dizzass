# Stage 10 — difficulty, target и математические поля work

**Модульные исходники и библиотеки, не готовый майнер. Физический T21 не подключался.**

Продолжение точного Stage 9: ZIP SHA-256
`1f590116a6aa8ed573b08495fe0aa3da412a36f65341010345356845fa650bba`.
Неизменённый `reference/cgminer.vendor.elf`: 6 228 004 байта, SHA-256
`b2663b3aa753cc14ae9d3b11a14d3d93c74b605a3e433b02101c3c17c69d95e9`.

## 1. Перенесённые вычисления

В `src/frontend/cgminer.c` добавлены три процедуры с новым явным API:

| Участок оригинала | Восстановленная часть |
|---|---|
| `0x2fe60..0x300ac` | Difficulty → 256-битный target, включая нулевой вход, выбор константы и разложение на четыре uint64 |
| `0x31070..0x31100` | Числовой участок target → difficulty, без последующего учёта результата |
| `0x30c9c..0x30d90` | Первый блок SHA-256, midstate и расчёт target при сборке work |

Размещение этих процедур во frontend — интеграционный выбор внутри ранее исследованного
кластера, не отдельное доказательство исходного имени каждой функции. Остальное содержимое
632-байтного work, владение указателями, строки и полный consumer не восстановлены.
Новый заголовок `include/xminer/recovery/difficulty.h` не является оригинальным ABI VNish.

### Difficulty → target

Оригинал вычисляет binary64-частное `base / difficulty`, затем последовательно выделяет
четыре 64-битные части, от старшей к младшей. Сохранены порядок операций, преобразования
между double/uint64 и округления промежуточных произведений и сумм. Это не замена на
произвольную «математически более точную» формулу и не деление рациональных чисел с
бесконечной точностью. Целочисленный target строится из уже округлённого частного double.

Точные константы из ELF:

- обычная ветвь: `0x1.fffep223` (binary64 `0x4defffe000000000`);
- только числовой селектор `1`: `0x1.fffep239` (`0x4eefffe000000000`).

Вторая базовая константа в 65 536 раз больше первой. Все остальные значения селектора
выбирают первую. **Эти числа не названы моделями ASIC или алгоритмами:** получение
селектора через оригинальный getter подменяется явным аргументом и не доказывает выбор T21.

`+0.0` и `-0.0` заменяются сложностью 1. Эта ветвь оригинала проверена отдельно.

### Обратный числовой участок

Сохранён порядок накопления limb `2, 3, 1, 0` с соответствующими степенями двойки.
Он важен для округлений double. При нулевом target оригинал подставляет знаменатель `1`,
поэтому результат равен выбранной базовой константе, **не сложности 1**. Результат всех
950 сравнений проверяется побитно как binary64.

### Математические поля work

Оригинальный участок:

1. Меняет порядок байтов внутри слов первых 64 байт уже собранного work.
2. Выполняет исходные SHA init/update/compression и пишет восемь слов midstate по `+0x80`.
3. Читает double difficulty по `+0x1a0` и пишет 32 байта target по `+0x100`.

В тестах исполняются SHA и target оригинала совместно. Все остальные байты 632-байтного
тестового work проверяются на неизменность. Это **не** свидетельство восстановления этих
остальных байтов. Новый API возвращает отдельную структуру midstate/target, не изображает
полностью восстановленный объект work. Проверки аргументов нового API выполняются до
записи результата; на отклонённых входах это не повторение побочных эффектов оригинала.

## 2. Ограничения арифметики и нового интерфейса

Контракт — IEEE binary64, обычный режим round-to-nearest, ties-to-even, без fast-math,
без расширенной точности промежуточных выражений и без слияния произведения со сложением.
Режим округления — **предусловие**, он не переключается и не проверяется этим API.
Задействованные в оригинале VMLA/VCVT воспроизведены отдельными действиями; FPSCR-флаги,
NaN-пэйлоады и нештатные режимы округления не моделируются.

Явно добавленные защиты нового C-интерфейса:

- NULL и нечисловая/бесконечная/отрицательная сложность → `VN135_VERIFY_INVALID` (`-2`);
- округлённое частное >= 2^256 либо недопустимое промежуточное преобразование →
  `VN135_DIFFICULTY_RANGE` (`-4`);
- выходной буфер не меняется при этих ошибках; конечные преобразования в uint64 не
  выполняются вне определённого диапазона C.

Это **наши защитные границы**, не заявление о наличии таких проверок в закрытой прошивке.
Очень большая положительная сложность может дать целочисленный target 0: это допускается
числовым API и не интерпретируется как действительная настройка пула.
`-ffast-math` и `-ffinite-math-only` отклоняются при компиляции на GCC и Clang; сохранён
`-ffp-contract=off` в Makefile и overlay. Не использовать этот модуль в окружении, которое
меняет FP-режим, без отдельного анализа.

## 3. Новая интеграционная связка, не исходный consumer

`reconstruction/support/work_difficulty_pipeline.c` добавляет отдельный адаптер:

```
nonce-кандидат + согласованный снимок задания + difficulty
    → target из difficulty
    → coinbase / Merkle / 112-байтный префикс (Stage 9)
    → префильтр nonce / SHA256d / сравнение с target (Stage 8)
```

Низкоуровневые старые API с явно передаваемым target сохранены. Новая функция не получает
задание из сети, не придумывает difficulty, не захватывает владение шаблоном и не гарантирует
его свежесть. Снимок, difficulty и селектор должны относиться к одному удерживаемому заданию.
`last_nonce` по-прежнему меняется до проверки хеша и не откатывается после отказа;
полноценная дедупликация с жизненным циклом заданий этим не создаётся.

При ошибке difficulty output/scratch/last_nonce остаются прежними. При дальнейшем отказе
действует контракт Stage 9. Нет выделения памяти, скрытых повторов, аппаратных команд или
передачи результата. Код возврата 0 означает завершённое вычисление, не accepted share.

Офлайн-пример `build/vn135-rebuild-genesis-difficulty` использует исторический вектор из
Stage 9, **теперь вычисляя target из difficulty=1**, а не беря готовый target из фикстуры.
Получает ожидаемый хеш первого блока Bitcoin. Флаги `job_freshness_checked`, `submitted`
и `hardware_tested` остаются false. Нативный тест воспроизводит синтетический RX с этим
nonce при фрагментации от 1 до 11 байт. Это не живые аппаратные данные или новый блок.

## 4. Проверяемые наборы

| Основные новые сравнения с оригинальными инструкциями | Случаев |
|---|---:|
| Difficulty → target; выполняются и оригинальные uint64/double helpers | 1 165 |
| Target → difficulty, сравниваются все биты double | 950 |
| Совместные midstate и target в work | 256 |
| **Основной новый набор** | **2 371** |
| Предыдущие наборы Stage 2–9 | 102 406 |
| **Совокупный основной набор** | **104 777** |

Новые три набора прошли на GCC и Clang. Повтор не увеличивает число уникальных входных
случаев. Отдельно, **без добавления к 2 371**:

- 60 композиций восстановленных участков caller/wrapper/prefix, target и проверки nonce;
  это несколько согласованных границ, не исполнение полного оригинального consumer;
- 33 независимых точных проверки для степеней двойки;
- 660 сравнений исходных процедур преобразования uint64/double с числовым эталоном;
- 1 302 синтетические проверки новых ARM/VFP-инструкций;
- 408 нативных C-проверок, в том числе 11 фрагментированных genesis-прогонов;
- 4 ожидаемых отказа компиляции для запрещённых FP-флагов.

Новый нативный набор прошёл GCC/Clang ASan/UBSan с проверкой утечек. Это не утверждение,
что все Python/ctypes сравнительные случаи запускались под ASan. ARMv7 библиотека собрана
freestanding, без Linux sysroot; это не исполняемый майнер.

### Граница эталона

Используется локальный ограниченный ARM-интерпретатор, не независимо сертифицированный
процессор/эмулятор. Новые инструкции VMOV (пара регистров), VMLA/VMLS, VCVT.u32/f64 и
VCMP #0 проверяются отдельно. Неизвестные инструкции/неподдержанные нечисловые операции
вызывают отказ теста. Внешние getter, memcpy и диагностика внедрены, SHA и оригинальные
числовые преобразования исполняются. Полный ELF как Linux-процесс не запускается.

Manifest сохраняет 6 участков/helper-диапазонов, 9 точных f64-констант и 17 связей BL.
`tools/check_stage10_evidence.py` проверяет эти байты, адреса, ссылки и ограничения API.
Не проверены физический ARM, всё множество входов, гонки, FPSCR-исключения, жизненный
цикл, аппаратная безопасность и принятие пулом. Число случаев не является покрытием
всего бинарника или процентом готовности.

## 5. Сборка и воспроизведение

```
make -f Makefile.recovery all arm stage10
make -f Makefile.recovery stage10-clang sanitize-stage10
./build/vn135-rebuild-genesis-difficulty
python3 tests/test_stage10_compile_policy.py
```

Полная проверка на чистой распаковке:

```
python3 tools/verify_stage10_all.py --logs /absolute/path/outside-source --workers 2
```

28 групп, с отдельной начальной сборкой Clang; результаты каждого запуска, ожидаемые
коды и SHA-256 логов записываются в `ALL_GROUPS.json`. Наличие runner не равно выполнению:
результат финального прогона поставленного архива передаётся отдельными логом и JSON.
`full-runtime` обязан вернуть 2 и не выдаёт «готовый майнер».

46 наблюдаемых путей; 7 частично восстановлены, 39 исключены. Компилируются 17 C-модулей
(7 наблюдаемых и 10 явно новых helper/adapter). 57 экспортируемых функций нового API —
не количество восстановленных оригинальных функций. Монолита и успешных заглушек нет.

**По-прежнему не восстановлены** полный 632-байтный work, строки/метаданные/владение,
полный consumer, очередь 72/68, жизненный цикл заданий, CRC ответов, выбор драйвера T21,
аппаратный запуск, PSU/датчики/охлаждение/защиты, драйвер upstream и автотюн. Полный public
cgminer не включён и его совместная сборка не заявляется. Механизм overlay сохранён,
старые исходники, авторство и объектные каталоги не заменены.

**Не заменять штатный `/usr/bin/cgminer`: это исходники и библиотеки, не прошивка.**
