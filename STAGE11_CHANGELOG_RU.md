# Stage 11 — строки, копирование и освобождение work

**Модульная реконструкция, не готовый T21 cgminer.** Физические ASIC, пулы и серверы не подключались. Исходный ELF сохранён:
`b2663b3aa753cc14ae9d3b11a14d3d93c74b605a3e433b02101c3c17c69d95e9`.

Продолжение Stage 10, ZIP SHA-256
`c2a3b670ef9bea63ea65e3db744787cb1216457bb90285493ae171f1f5962acb`.

## 1. Что добавлено в C

В существующем `src/frontend/cgminer.c` реализованы следующие исследованные участки. Размещение во frontend — интеграционный выбор внутри уже обнаруженного кластера, а не отдельное доказательство исходного имени каждой процедуры.

| Участок оригинала | Восстановленная часть |
|---|---|
| `0x30a6c–0x30a9c` | Копирование 64 бит difficulty и трёх строк шаблона в независимые выделенные буферы |
| `0x2ce84–0x2d108` | Копирование work, **только ветвь с нулевым аргументом изменения времени** |
| `0x2a1bc–0x2a328` | Освобождение четырёх строк и обнуление 632 байт самого work |
| `0x2a330–0x2a4a0` | Освобождение строк, затем объекта и обнуление указателя вызывающего кода |
| `0x30d90–0x30db8` | Ограниченный набор записей в поля builder |
| `0x303e8–0x3043c` | Ограниченный набор записей wrapper и инкремент слова `reference + 0x98` |

Конечные адреса в таблице не включаются. Новые имена API и заголовок `include/xminer/recovery/work_storage.h` не являются восстановленными именами/ABI VNish.

### Метаданные

Три строки копируются в порядке `work + 0x18c`, `+0x1a8`, `+0x19c`. Источники — указатели `template + 0x3d0`, `+0x3ec` и встроенная строка по `+0x396`. Difficulty переносится побитно с `template + 0x3a8` в `work + 0x1a0`; эта процедура не проверяет её числовую допустимость. Даже тестовые NaN-битовые комбинации сохраняются как данные, без арифметики.

**Отказ выделения одной строки не прекращает следующие вызовы копирования в этом участке.** В новом интерфейсе введены `PARTIAL` и маска отсутствующих строк. Это новые диагностические результаты, не обнаруженный код возврата оригинальной процедуры. Частичные выделения остаются собственностью объекта и доступны для очистки. Это наблюдение ограниченного участка, не заключение об обработке ENOMEM во всей прошивке.

### Копия work без изменения времени

Оригинал выделяет 632 байта, получает значение сериализованного глобального счётчика и увеличивает его, копирует изображение исходного work, заменяет поле `+0x1bc` и независимо дублирует четыре присутствующие строки. Порядок копирования: `18c → 1a8 → 19c → 1b0`.

В новом API идентификатор передаётся явно. Оригинальная глобальная таблица, mutex и выделение уникальных номеров в многопоточном runtime не создаются. В эталоне проверены исходные инструкции изменения счётчика и успешные lock/unlock; это не проверка реальной конкурентности.

Ненулевая ветвь изменения времени (`r1 != 0`) **не восстановлена**. Нельзя применять новый API как реализацию полного оригинального clone/roll-work для любых аргументов.

### Очистка и удаление различаются

Порядок освобождения строк: `18c → 19c → 1b0 → 1a8` — он отличается от порядка копирования. `clear` затем обнуляет 632 байта и сохраняет внешний объект. `delete` дополнительно освобождает сам объект и записывает NULL в указатель вызывающего кода. Диагностика оригинального delete(NULL) отмечена в тесте, но не воспроизводится в библиотеке.

Другие поля-ссылки этими процедурами не освобождаются. Следовательно, этот этап **не восстанавливает полное владение pool/template/job и не доказывает их актуальность**. Очистка не заявляется криптографически гарантированным стиранием памяти.

### Два небольших участка присваиваний

Builder записывает `0x53` по `+0x250`, сырую ссылку по `+0x16c`, `60` по `+0x15c`, ноль по `+0x160` и глобальное слово по `+0x1b8`.

Wrapper записывает несколько сырых полей, байт `1` по `+0x180` и увеличивает `reference + 0x98` по модулю 2^32. Назначение этого счётчика **не объявлено refcount** без анализа всей работы с ним. Указатели представлены явными 32-битными cookies; они не разыменовываются новым API.

## 2. Представление памяти: не подмена оригинального ABI

`vn135_work_storage` содержит:

- массив из **632 байт** с непрозрачными полями;
- отдельно четыре нативных указателя на принадлежащие объекту строки и их длины.

Четыре известных 32-битных указательных слота `18c/19c/1a8/1b0` в массиве **всегда нулевые**. В сравнениях оригинальные ARM-указатели нормализуются в эти нулевые слоты, а строки сравниваются отдельно. Все остальные байты изображения сверяются побайтно — это подтверждение копирования, а не понимание смысла каждого поля.

**Этот тип не совместим с исходным бинарным ABI.** Его нельзя приводить к указателю оригинального work, отправлять в оригинальную очередь или сериализовать как готовый объект VNish. Существующие противоречия 68/72 байта очереди не решены этим этапом.

Неизвестные поля не получают выдуманного смысла. Нового полного конструктора из нулей и полной замены 632-байтного work нет. Для тестов используются явно синтетические изображения, строки и cookies.

## 3. Новый адаптер с откатом неполной копии

`reconstruction/support/work_storage_pipeline.c` содержит отдельный `vn135_work_clone_atomic`:

1. вызывает восстановленный вариант копирования;
2. при частичном отказе освобождает все успешно выделенные строки и саму неполную копию;
3. не публикует выходной указатель, пока копия не готова.

Это **новая транзакционная политика, не найденная в VNish**. Слово atomic означает «не публиковать неполный результат», а не lock-free, аппаратную атомарность или потокобезопасность. Отказ выделения внешнего объекта также обработан новым guard; эталон оригинала для этого события не объявляется проверенным.

Новые проверки интерфейса отклоняют неверные указатели/размеры, встроенный NUL, отсутствующие обязательные строки, занятый выход и нарушенную нормализацию указателей до побочных эффектов. Однако API не проверяет действительность произвольного адреса. Буферы должны быть доступны в указанном размере; принадлежащие объекту строки — отдельными выделениями той же пары allocator/free. Общие объекты требуют внешней синхронизации. Входы, выходы и маски ошибок не должны опасно перекрываться.

## 4. Выполненные новые проверки

| Сравнение нового C с оригинальными ARM-инструкциями | Случаев |
|---|---:|
| Метаданные, три строки, все варианты отказа их выделения | 576 |
| Копия без изменения времени, комбинации отсутствующих строк/отказов | 486 |
| Clear и delete, порядок освобождения и состояние объекта | 384 |
| Поля builder и wrapper; неизменность остальных байтов | 640 |
| **Основные новые сравнения Stage 11** | **2 086** |

Все четыре набора прошли на GCC и Clang. Повтор на другом компиляторе не добавляется к числу уникальных входов. Прежний основной набор содержит 104 777 сравнительных случаев; вместе набор содержит **106 863**. Факт повторного полного прогона поставленного ZIP подтверждается отдельными финальными логом и JSON, не одним существованием тестов.

Дополнительно выполнены **1 200 нативных сценариев / 12 220 утверждений** с настоящими `malloc/free`, включая отказы внешнего выделения, частичные строки, откат нового адаптера, повторную очистку, NULL/границы и независимость копии. Этот набор прошёл GCC/Clang, ASan/UBSan с `detect_leaks=1`. Санитайзеры относятся к нативному C-набору, не ко всем Python/ctypes сравнениям.

В офлайн-сценарии соединены метаданные, копирование, очистка оригинала и хеширование заголовка из сохранившейся копии. Получен известный SHA256d fixture первого блока Bitcoin, ранее проверенной в Stage 9. **Это фиксированные исторические данные, не живая шара, не найденный блок и не проверка lifecycle реального пула.**

### Как устроен эталон

Исходные ARM-инструкции выполняются в прежнем локальном ограниченном интерпретаторе. На этом этапе его набор инструкций не менялся. Исходное тело `strdup` (`0x5a38a0`) исполняется, а `strlen`, `malloc/calloc/free`, memcpy/memset, mutex и диагностика заменены явными ограниченными обработчиками. Для clone внешнее выделение в эталоне успешно; отказы копирования строк инъецируются отдельно. Исключения ctypes-callbacks считаются ошибками теста.

Проверяются состояние, порядок внешних событий, содержимое строк, идентификатор, счётчик, неизменность источника и нормализованные байты. Интерпретатор не является независимо сертифицированным CPU и не запускает полный ELF как процесс. Нет проверки гонок, всей прошивки, физического ARM или оборудования.

## 5. Доказательства, сборка и продолжение

`evidence/stage11/recovery-manifest.json` фиксирует **7 диапазонов кода, 5 блоков литералов и 20 рёбер переходов** с исходными адресами, SHA-256 и листингами. Количество диапазонов не равно числу полностью восстановленных функций.

```sh
make -f Makefile.recovery all arm stage11
make -f Makefile.recovery stage11-clang sanitize-stage11
./build/vn135-work-lifecycle
python3 tools/check_stage11_evidence.py
python3 tools/verify_stage11_all.py --logs /absolute/path/outside-source --workers 2
```

Компилируются **18 C-модулей**: 7 на наблюдаемых путях и 11 явно новых helper/adapter. Всего наблюдались 46 путей, 39 по-прежнему исключены. Это не процент восстановления. Монолитных файлов и успешных заглушек нет.

Полное дерево public cgminer в архив не включено, полная совместная сборка upstream не заявляется. Механизм additive-overlay и защита от перезаписи исходных файлов сохранены. ARMv7-библиотека freestanding, без Linux sysroot; не исполняемый майнер.

**Остаются:** ненулевая ветвь time-roll, полная семантика/метаданные work, владение внешними ссылками и полный consumer, очередь 72/68 и актуальность заданий, CRC ответов, выбор драйвера моделью T21, запуск цепей, PSU/датчики/охлаждение/защиты, runtime-интеграция cgminer и автотюн.

**Не заменять штатный `/usr/bin/cgminer` этим комплектом.** `full-runtime` должен возвращать отказ, а не создавать фиктивную готовую прошивку.

Патч Stage 10 → Stage 11 не включает собственную копию и самоссылочный инвентарь. После применения нужно выполнить `python3 tools/update_overlay_inventory.py --write`. Полный ZIP — основной самодостаточный комплект.
